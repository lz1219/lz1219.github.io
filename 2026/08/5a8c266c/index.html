PostgreSQL 实战手册（四）：性能分析与 SQL 调优

系列第四篇，也是整个系列最讲”诊断动作”的一篇。延续 shop 演示库，基于 PostgreSQL 16。本文不讲”索引很有用”这种废话，只回答三个问题：慢 SQL 在哪、为什么慢、怎么修。

系列目录：一、基础命令与日常管理 ｜ 二、函数与存储过程 ｜ 三、视图与常用函数精讲 ｜ 四、性能分析与 SQL 调优 ｜ 五、事务、MVCC 与锁

一、慢 SQL 在哪：两个定位工具

1.1 慢查询日志（零成本，先开）

超过 500ms 的语句会带执行计划参数写进日志。生产建议 200ms~1s 起步，按基线调。

1.2 pg_stat_statements：慢 SQL 的账本（必装）

它把 SQL 归一化（参数替换成 $1）后按模板聚合统计。查 Top 慢 SQL：

排序按总耗时而不是平均耗时——平均 1ms 但每秒被调一万次的 SQL 比偶尔 10s 的报表更伤系统。pct 列直接告诉你优化哪条收益最大。

二、为什么慢：EXPLAIN 逐行解读

2.1 正确的打开方式

EXPLAIN 只看计划（估算）；ANALYZE 真的执行并给出实际数据（写语句慎用，会真改数据，可包在事务里 ROLLBACK）；BUFFERS 显示缓存命中，是判断 IO 瓶颈的关键，漏了它等于白看。

2.2 一行计划的所有字段

  • cost=0.43..8.45：启动代价..总代价，单位是抽象成本（以顺序读一页为 1），只用于比较计划之间，不代表毫秒
  • rows=1：估算返回行数
  • actual time=0.031..0.032：实际启动毫秒..实际完成毫秒
  • rows=2 loops=1：实际行数、节点被执行次数。嵌套循环内侧节点 loops 会很大
  • Index Cond：走索引的条件；与之对应 Filter 是拿到行之后再过滤的——Filter 干掉大量行 = 索引没帮上忙的信号
  • Buffers: shared hit=4：4 页命中共享缓存；出现大量 read= 是从磁盘读，temp read/write 是内存不够用了临时文件（work_mem 太小）
  • 末尾 Planning Time / Execution Time：优化器耗时与执行耗时分开看，准备语句场景前者重要

2.4 常见节点类型速查

节点 含义 该警惕什么
Seq Scan 全表顺序读 大表 + 高过滤性条件 = 缺索引；小表则是合理选择
Index Scan 索引定位 + 回表取行 回表多时考虑覆盖索引
Index Only Scan 索引覆盖全部所需列，不回表 最快形态；但依赖 visibility map，表刚大批量更新后可能退化
Bitmap Heap Scan 索引收集多个页地址后批量回表 中等选择度的正常形态
Nested Loop 外侧每行驱动内侧查一次 外侧估算偏小会爆炸性放大内侧 loops
Hash Join 小表建哈希大表探测 看到 Batches: 8 说明 work_mem 不够，哈希溢写了磁盘
Sort / Incremental Sort 排序 Sort Method: external merge Disk = work_mem 不足

三、怎么修：索引选型与写法

3.1 PG 的索引家族（这是比 MySQL 丰富得多的地方）

类型 适用 例子
B-tree（默认） 等值、范围、排序，万能 CREATE INDEX i ON orders(user_id)
GIN 多值包含：数组、JSONB、全文检索 CREATE INDEX i ON products USING GIN (attrs)
GiST 几何、范围重叠、最近邻 CREATE INDEX i ON rooms USING GIST (location)
BRIN 超大表且物理顺序与值相关（如按时间追加的日志） CREATE INDEX i ON logs USING BRIN (created_at)，体积只有 B-tree 的千分之一
Hash 纯等值 实战中基本都被 B-tree 替代，知道即可

3.2 三个省一个亿的高级写法

3.3 复合索引的列序口诀

等值在前，范围在后：(user_id, status, created_at) 能服务 user_id=? AND status=? AND created_at>?，但对 status=? 单独查询基本无用（前导列缺失）。给查询建索引，不是给表建索引。

3.4 索引失效/无感的典型场景

  • LIKE '%abc' 前导通配符，B-tree 用不上——装 pg_trgm 扩展 + GIN 索引可解
  • 对列做运算：WHERE created_at::date = '2026-08-08' 索引失效，改范围 created_at >= '2026-08-08' AND created_at < '2026-08-09'，或建表达式索引
  • 隐式类型不匹配：参数类型与列类型不一致导致索引列被强转（JDBC 里 setString 对 bigint 列是经典事故）

五、避坑指南：调优的五个纪律

  1. 先看 pg_stat_statements 再动手——拍脑袋优化的对象常常根本不是瓶颈，pct 列决定优先级
  2. EXPLAIN 不带 BUFFERS 等于白看——hit vs read 是内存瓶颈与索引问题的分水岭
  3. 估算错先 ANALYZE，别急着改 SQL——八成的”优化器犯傻”是统计信息过期
  4. 建索引想写入成本——每个索引都拖慢 INSERT/UPDATE，pg_stat_user_indexes 里 idx_scan = 0 的索引定期清理
  5. 改参数先 ALTER SYSTEM 小步试——work_mem 是按每个排序/哈希节点分配的，并发高时全局调大会撑爆内存

总结

  • 定位：log_min_duration_statement 抓现行，pg_stat_statements 算总账（按总耗时排序）
  • 诊断：EXPLAIN (ANALYZE, BUFFERS) 三件套；核心看估算 rows vs 实际 rows 和 Filter 丢弃量、Buffers 的 read/temp
  • 修复：等值在前范围在后的复合索引、部分索引、表达式索引、INCLUDE 覆盖索引
  • PG 特有武器：GIN（JSONB/数组）、BRIN（巨型时序表）、扩展统计 CREATE STATISTICS
  • 深分页用键集、count 用估算、锁问题用 pg_blocking_pids 一条 SQL 看清阻塞链

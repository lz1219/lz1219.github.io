MySQL 实战手册（四）：性能分析与 SQL 调优

系列第四篇。调优的第一原则：先测量，再优化。本篇按”发现问题 → 读懂执行计划 → 优化索引与 SQL → 排查锁与服务器”的实战顺序展开。EXPLAIN 的每一列都讲透，这是中级和初级的分水岭。演示数据用第二篇 GenOrders(10000) 生成的 1 万条订单。

系列目录：一、基础命令与日常管理 ｜ 二、存储过程与自定义函数 ｜ 三、视图与常用函数精讲 ｜ 四、性能分析与 SQL 调优 ｜ 五、事务与锁

一、慢查询日志：问题 SQL 的入口

日志逐条看效率低，用工具聚合：

排查优先级看”总耗时 = 单次耗时 × 次数”——每秒 10 次的 200ms 查询，比一天一次的 5s 查询危害大得多。pt-query-digest 的报表默认就是按总耗时排序的。

二、EXPLAIN 逐列拆透

返回 12 列，按排查时的真实关注顺序讲。

2.1 type：访问类型（最重要的一列）

从优到劣的完整序列，记到能默写：

type 含义 出现场景
system 表只有一行 系统表，业务库几乎看不到
const 主键/唯一索引等值查询，最多一行 WHERE id = 1
eq_ref JOIN 时驱动表的每行在被驱动表只命中一行（唯一索引关联） JOIN ON u.id = o.user_id 中查 users 一侧
ref 非唯一索引等值查询 WHERE user_id = 1（普通索引）
fulltext 全文索引 MATCH AGAINST
ref_or_null ref 的基础上还查 NULL WHERE user_id = 1 OR user_id IS NULL
index_merge 索引合并：多个二级索引取交/并集 WHERE a = 1 OR b = 2（两列各有索引时可能出现）
range 索引范围扫描 > < BETWEEN IN LIKE 'x%'
index 扫整棵二级索引（比 ALL 快但仍是全量） 覆盖索引但无 WHERE 命中索引前缀
ALL 全表扫描 红旗，除非表很小否则必须处理

经验值：OLTP 查询至少做到 range，热点查询要做到 ref 以上。

2.2 key 与 possible_keys：用了哪个索引

  • possible_keys：优化器认为可以用的索引（候选名单）
  • key：实际选择的索引，NULL 就是没用索引

有候选但最终 key = NULL，说明优化器评估走索引不如全扫（常见于结果集占表比例过大，比如 status 只有两种值、命中率 50%）——这种不是索引失效，是优化器的理性选择，别瞎加 hint。

2.3 key_len：判断联合索引用了几列（高手分水岭）

key_len 是实际使用的索引字节数，反推联合索引用到第几列。计算规则：

  • 定长类型：INT=4，BIGINT=8，DATETIME=5（8.0），DECIMAL(10,2)=5
  • 变长 VARCHAR(n)：字符集每字符最大字节 × n，再加 2 字节长度前缀。utf8mb4 下 = 4n + 2
  • 允许 NULL 的列：再 +1 字节

实战例子：索引 idx_user_status (user_id, status)，其中 user_id BIGINT UNSIGNED NOT NULL（8 字节），status VARCHAR(16) NOT NULL（4×16+2=66 字节）：

看 key_len 就知道”联合索引吃到第几列”，不用猜。

2.4 rows 与 filtered：扫描量和命中率

  • rows：预估要扫描的行数（基于统计信息，可能严重偏离实际）
  • filtered：扫描行中预计满足条件的百分比

rows × filtered% ≈ 最终返回行数。rows=10000, filtered=10 意味着扫一万行只留一千——扫描效率差，考虑更精准的索引。

2.5 Extra：附加信息全清单

Extra 值 含义 评价
Using index 覆盖索引：查询列全在索引里，不回表 ✅ 好
Using where 存储引擎返回行后，Server 层再过滤 中性，配合大 rows 时关注
Using index condition ICP 索引下推：WHERE 中索引列的条件在引擎层提前过滤，减少回表 ✅ 好（8.0 默认开启）
Using MRR 多范围读优化：回表前先把主键排序，变随机 IO 为顺序 IO ✅ 好
Using filesort 排序没走索引，内存/磁盘另起排序 ⚠️ 红旗
Using temporary 用了临时表（常见于 GROUP BY 无索引支撑） ⚠️ 红旗
Using join buffer (hash join) 无索引 JOIN，走哈希连接（8.0.18+） ⚠️ 小表可忍，大表要加索引
Impossible WHERE 条件永远为假，优化器直接返回空 检查是不是写错了条件
Select tables optimized away 聚合函数（MIN/MAX 等）被索引直接优化掉 ✅ 很好
Using index for group-by Loose Index Scan，GROUP BY 直接利用索引序 ✅ 好

2.6 id 与 select_type：多表/子查询的执行顺序

  • id 相同：同层级，从上往下执行（上面的先驱动）
  • id 不同：id 大的先执行（子查询先跑）
  • id = NULL：UNION 的合并结果集

select_type 标明该行的角色：

select_type 含义
SIMPLE 无子查询无 UNION 的简单查询
PRIMARY 含子查询时的最外层查询
SUBQUERY SELECT/WHERE 中的标量子查询
DEPENDENT SUBQUERY 相关子查询（依赖外层值，逐行执行，性能杀手）
DERIVED FROM 里的派生表（8.0 通常会合并优化掉）
UNION / UNION RESULT UNION 的第二及后续 SELECT / 合并结果

看到 DEPENDENT SUBQUERY 要本能地改写成 JOIN 或窗口函数。

2.7 另外三列

table（该步访问的表/别名）、partitions（命中的分区，分区表才有意义）、ref（与索引比较的值来源，如 const 或驱动表的列 shop.u.id）。

九、调优策略总结

按顺序执行，解决 90% 的性能问题：

  1. 定位：慢日志 + pt-query-digest，按总耗时排序
  2. 解读：EXPLAIN 看 type/key/key_len/rows/Extra；EXPLAIN ANALYZE 验证预估与实际偏差
  3. 优化：先索引（列序、覆盖、隐身灰度），再 SQL（去函数、游标分页/延迟关联、拆 OR），最后架构（读写分离、分库分表）
  4. 排锁：计划正常但慢 → data_lock_waits + 长事务
  5. 验证：优化前后 EXPLAIN ANALYZE 对比实际耗时，用数据说话

最后一句实话：绝大多数慢查询靠”合适的索引 + 不在索引列上乱用函数”就能治好，玄学的空间很小。

一、慢查询日志：问题 SQL 的入口

生产环境更推荐 pt-query-digest，能输出每类查询的执行次数、平均/最大耗时、锁等待占比的完整报告。排查优先级看”总耗时 = 单次耗时 × 次数”，而不是单次最慢的那条——每秒 10 次的 200ms 查询比一天一次的 5s 查询危害大得多。

死锁排查

死锁（错误码 1213）的预防原则：所有事务按固定顺序访问行（比如都按 id 升序更新）；SELECT ... FOR UPDATE 只在必要时用；应用层对 1213 做有限次重试 + 退避。高并发争抢同一行的场景（库存扣减），考虑把隔离级别从默认的 REPEATABLE READ 降为 READ COMMITTED，间隙锁消失后死锁率明显下降：

五、调优策略总结

按顺序执行这套流程，能解决 90% 的 MySQL 性能问题：

  1. 定位：慢查询日志 + pt-query-digest，按”总耗时”排序找目标
  2. 解读：EXPLAIN 看 type/key/rows/Extra，EXPLAIN ANALYZE 验证预估与实际是否偏离
  3. 优化：优先改索引（联合索引列序、覆盖索引、隐身索引灰度验证），其次改 SQL（去函数、游标分页、UNION ALL 替 OR），最后才考虑改架构（读写分离、分库分表）
  4. 排锁：慢但 EXPLAIN 正常 → 查 data_lock_waits 和长事务
  5. 验证：优化前后用 EXPLAIN ANALYZE 对比实际耗时，用数据说话

最后一句实话：绝大多数慢查询靠”合适的索引 + 不在索引列上乱用函数”就能治好，玄学的空间很小。

MySQL 实战手册（五）：事务与锁

系列第五篇，讲 MySQL 最核心也最容易出事故的部分。事务和锁是”平时感觉不到、出事就是大事”的典型——超卖、脏数据、死锁告警，根子都在这里。本篇基于 InnoDB（MySQL 8.0），沿用系列前四篇的 shop 库。

系列目录：一、基础命令与日常管理 ｜ 二、存储过程与自定义函数 ｜ 三、视图与常用函数精讲 ｜ 四、性能分析与 SQL 调优 ｜ 五、事务与锁

一、事务基础与 ACID

ACID 一句话版：Atomicity 全做或全不做（undo log 实现）；Consistency 数据满足约束；Isolation 并发互不干扰（锁 + MVCC 实现，本篇主角）；Durability 提交后不丢（redo log 实现）。

避坑指南：事务边界的四个坑

  1. DDL 会隐式提交：事务中执行 ALTER TABLE / CREATE TABLE，前面未提交的 DML 会被静默提交——DDL 永远不要混在业务事务里
  2. autocommit = 1（默认）时每条语句独立事务，应用框架里”以为在一个事务里”但实际没开 @Transactional，是最常见的数据不一致来源
  3. 长事务是万恶之源：撑爆 undo log、阻塞 purge、挡住 DDL，还放大锁冲突概率。事务里严禁做 RPC 调用、发消息、读文件这类 IO
  4. 批量更新拆小事务：UPDATE ... WHERE id BETWEEN x AND y 每批几百~几千条，别一个大事务改几百万行

二、并发三问题与四种隔离级别

隔离级别 脏读 不可重复读 幻读 说明
READ UNCOMMITTED ❌ 有 ❌ 有 ❌ 有 基本不用
READ COMMITTED ✅ 无 ❌ 有 ❌ 有 每句 SELECT 读最新已提交数据；Oracle/PG 默认
REPEATABLE READ（MySQL 默认） ✅ 无 ✅ 无 ✅ 基本无 事务内快照一致，靠 MVCC + 间隙锁防幻读
SERIALIZABLE ✅ 无 ✅ 无 ✅ 无 退化为加锁读，并发差，慎用

术语辨析（很多人搞混）：

  • 脏读：读到别人未提交的数据（最恶劣）
  • 不可重复读：同事务内两次读同一行，值变了（别人改了并提交）
  • 幻读：同事务内两次同条件查询，行数变了（别人插入/删除了符合条件的行）

三、MVCC：读写不互斥的秘密

RR 级别下，普通 SELECT 是快照读，不加锁，自然快——这就是 MVCC（多版本并发控制）的功劳。三个关键机制：

  1. 隐藏列：每行数据带 DB_TRX_ID（最后修改它的事务 ID）和 DB_ROLL_PTR（指向旧版本的回滚指针）
  2. undo log 版本链：每次更新把旧值存入 undo log，形成历史版本链
  3. ReadView：快照读时生成，决定”哪个版本对我可见”——RR 在事务第一次快照读时创建（之后一直用同一个，所以可重复读）；RC 在每条 SELECT 都新建（所以能看到别人刚提交的）

快照读 vs 当前读（关键区分）

避坑：快照读和当前读混用会产生”查到的和改到的不一样”的诡异现象——SELECT 看到库存 10（快照），UPDATE 时实际已变 5。要先 FOR UPDATE 锁定再决策，或直接用条件更新（见文末库存案例）。

四、InnoDB 锁体系

锁的类型

锁 粒度 说明
Record Lock 行 锁单条索引记录
Gap Lock 间隙 锁记录之间的间隙，防插入（RR 特有）
Next-Key Lock 行+间隙 记录锁 + 前面间隙，RR 下当前读的默认单位（左开右闭）
意向锁（IS/IX） 表 加行锁前自动加，用于表锁冲突检测，不用手动管
表锁 表 LOCK TABLES，InnoDB 下基本不用

必须理解的要点

  1. 行锁锁的是索引，不是物理行。UPDATE ... WHERE name = 'x' 而 name 无索引 → 锁不上具体行，退化成全表逐行加锁，效果等同锁表！这就是”没索引的 UPDATE 会锁全表”的真相，也是第一篇强调 DML 走索引的深层原因
  2. 间隙锁只为防止幻读插入，RC 级别没有间隙锁——这就是高并发下建议 RC 的原因
  3. 唯一索引的等值查询，Next-Key Lock 退化为 Record Lock（锁范围最小）；范围查询和非唯一索引则会加间隙锁，范围比直觉大

加锁规则：四种典型场景（RR 级别，当前读）

这是锁部分最硬的骨头，用具体例子消化。准备数据：orders 表 id 主键 1~5，user_id 普通索引，status 无索引。

场景 1：唯一索引等值，命中记录

退化为 Record Lock，只锁 id=3 这一行。锁范围最小，并发最友好。

场景 2：唯一索引等值，未命中

退化为 Gap Lock，锁住”7 应该出现的位置”的间隙（比如 5~10 之间），防止别的事务插入 7 造成幻读。不存在的记录也占锁，这是很多人没想到的。

场景 3：非唯一索引等值

Next-Key Lock 锁住该值区间 + 前后间隙：锁 user_id=2 的所有行，外加 2 的前面和后面间隙（阻止插入新的 user_id=2 记录）。非唯一索引等值的锁范围比唯一索引大得多。

场景 4：范围查询

Next-Key Lock 覆盖 (3, 6]，即 4、5 两行 + (3,4] 间隙。注意右边界是闭的——id=6 本身也会被锁，这是 Next-Key 左开右闭特性，容易误判阻塞范围。

无索引列的 WHERE（重申，因为太重要）

锁不上具体行 → 全表逐行 Next-Key Lock，效果等同锁全表。低峰期执行也得小心。

锁兼容速查

共享锁 S 排他锁 X
S ✅ 兼容 ❌ 互斥
X ❌ 互斥 ❌ 互斥

快照读（普通 SELECT）不加锁，与 S/X 都不冲突——MVCC 的意义就是让”读”和”写”在大多数情况下不互相阻塞。

五、死锁：实战排查与预防

经典死锁场景（可亲手复现）

A 持 1 等 2，B 持 2 等 1——环路形成，InnoDB 检测到后牺牲代价小的事务回滚。

预防五条军规

  1. 固定访问顺序：所有事务都按 id 升序更新多行，环路无法形成（上面案例改成同序就不再死锁）
  2. 缩短事务：锁持有时间越短，撞锁概率越低；事务内禁止 IO
  3. 索引要到位：无索引的 UPDATE 锁全表，是生产死锁的头号帮凶
  4. 热点行争用（库存、计数器）：考虑 READ COMMITTED（消除间隙锁）或队列化/分桶拆分热点
  5. 应用层必须重试：1213 是常态而非异常，重试 23 次 + 随机退避（50200ms），别直接报错给用户

方案三：乐观锁（低冲突场景）

无锁等待、吞吐高，但高冲突下重试风暴反而更慢。读多写少用乐观锁，写多读少用条件更新/悲观锁。

七、隔离级别选型建议

  • 默认 RR 适合大多数业务：快照一致，配合间隙锁防幻读
  • 高并发热点（秒杀、计数器）建议 RC：无间隙锁、死锁少、undo 更小；主从复制需配合 binlog ROW 格式（8.0 默认就是 ROW，无后顾之忧）
  • 切换方式：全局 transaction_isolation = 'READ-COMMITTED'，或关键事务 SET SESSION 局部切换

总结

  • 事务：边界要小、不含 IO、不混 DDL、批量拆小
  • MVCC：普通 SELECT 是不加锁的快照读；FOR UPDATE 和 DML 是加锁的当前读，两者看到的世界可能不同
  • 锁：行锁锁索引，没索引的 DML 等于锁表；RR 有间隙锁，RC 没有
  • 死锁：固定顺序、缩短事务、1213 必重试
  • 选型：一般业务 RR，热点争抢 RC，库存用条件更新兜底防超卖

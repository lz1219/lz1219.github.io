MySQL 实战手册（二）：存储过程与自定义函数

系列第二篇，讲数据库端编程。存储过程和函数适合把多步数据操作封装在数据库内执行（减少网络往返、保证原子性），但用不好就是性能和可维护性的双重灾难。本篇沿用第一篇的 shop 库。

五、游标（能不用就不用）

游标用于逐行处理结果集：

避坑指南：游标是性能重灾区

  1. 逐行处理本质是 N 次单条 SQL，能改写成一条集合操作（UPDATE…WHERE / INSERT…SELECT）就坚决改写，性能通常差一个数量级
  2. NOT FOUND HANDLER 必须配合 SET v_done = 1 模式，否则循环变死循环
  3. HANDLER 声明顺序有讲究：变量、游标、HANDLER，写错顺序直接报错

六、自定义函数（FUNCTION）

函数必须有返回值、可在 SQL 语句中嵌套调用：

存储过程 vs 函数

对比项 存储过程 自定义函数
返回值 0~多个结果集 + OUT 参数 必须返回单个标量值
调用方式 CALL 可嵌在 SELECT/WHERE 里
事务控制 可以 START/COMMIT 不允许
副作用 可增删改数据 设计上应只读计算

避坑指南：函数的四个坑

  1. WHERE 里套函数 = 索引失效：WHERE OrderLevel(amount) = '大单' 全表扫描，改成范围条件 WHERE amount >= 200；同理 WHERE DATE(created_at) = '2026-08-01' 应改范围查询
  2. 开启 binlog 的库创建函数会报错：设 log_bin_trust_function_creators = 1，或声明 DETERMINISTIC / NO SQL 解决
  3. 非 DETERMINISTIC 的函数（用了 RAND()/NOW()）在主从复制下可能导致从库数据不一致
  4. 函数里不能写动态 SQL（PREPARE），存储过程才可以——而动态 SQL 要防注入

七、管理与维护

MySQL 的存储过程不支持修改，只能 DROP 后重建——所以定义务必纳入版本管理（Git），别只存在数据库里。备份时记得 mysqldump --routines（第一篇的坑在这里回收）。

总结

存储过程适合：批量造数、多步原子操作、定时维护任务。不适合：复杂业务逻辑（调试难、无法单测、版本管理弱）。SQL 能一条写完的不用游标，应用层能算清楚的不用函数。

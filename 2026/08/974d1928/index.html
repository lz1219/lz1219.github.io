上下文工程（二）：AGENTS.md 深度实践——写出+4%的上下文文件，避开-3%的坑

发表于2026-08-14|更新于2026-08-14|技术
|浏览量:

2026 年 2 月，ETH Zurich 的研究者在 438 个真实编码任务上做了一组对照实验，得出一个让很多人需要重新审视自己仓库的结论：LLM 自动生成的上下文文件让任务成功率下降约 3%，人工精心编写的提升约 4%——而两者都让推理成本上涨超过 20%。 AGENTS.md 不是”有比没有好”，而是”准比有重要”。本文讲清楚那 7 个百分点的差距到底在哪里。

一、先理解那组实验：-3% 和 +4% 之间隔着什么

Evaluating AGENTS.md（arXiv 2602.11988）在 SWE-bench Lite 和新基准 AGENTbench 上测试了上下文文件对编码 Agent 的真实影响。数字背后的机理比数字本身更重要：

自动生成的文件为什么帮倒忙？ 因为它们的内容是”正确的废话”：项目简介、泛泛的架构描述、从 README 抄来的 Getting Started。这些信息 Agent 自己扫一眼仓库就能得到，写进文件里只会：

  • 挤占宝贵的注意力配额（Context Rot：每个低质量 token 都在稀释高质量 token）；
  • 增加 20%+ 的推理成本；
  • 制造”文档与现实不符”的冲突风险（Context Clash）。

人工编写的文件为什么有效？ 因为它们写的是 Agent 靠自己发现不了、但一犯就错的东西：精确的构建命令、明确的禁区、真实踩过的坑。一句话概括：

AGENTS.md 的价值 = 它包含的”反事实信息”密度——写下的是”如果不写，AI 就会犯错”的内容，而不是”写出来好看”的内容。

二、长度纪律：最没有争议也最容易做错的部分

先立三条有出处的硬约束：

  1. 前沿模型能稳定遵循的指令总量约 150~200 条，超过后遵守率快速衰减；小模型更差，随指令数量指数级下降。
  2. 位置偏见真实存在：模型高度关注上下文开头和结尾，夹在中间的超长文件容易沦为”被遗忘的中间层”。
  3. 参照系：HumanLayer 生产环境的主 CLAUDE.md 控制在 60 行以内；社区实验从 3000 字砍到 800 字效果持续改善；vercel/vercel 这种复杂 monorepo 的根文件 247 行；社区共识是普通项目 ≤300 行，超过 500 行必须按子模块分片。

落地成一个自问自答的习惯：每写一行，问一句”如果没有这句话，AI 真的会犯错吗？” 答不上来就删。

三、结构：WHAT / WHY / HOW 三要素，外加两块压舱石

HumanLayer 总结过一份优秀 AGENTS.md 的”三要素”：

  • WHAT（地图）：技术栈是什么？项目结构怎样？（monorepo 里哪个是 App、哪个是 Lib 必须说清）
  • WHY（目标）：项目的核心价值是什么？核心模块的职责边界在哪里？
  • HOW（工具）：怎么构建？怎么跑测试？用 npm 还是 pnpm？

在此之上，两份”压舱石”章节被证明 ROI 最高：

  • CRITICAL RULES（红线）：绝对禁止的操作，用词必须是 NEVER / ALWAYS / MUST 级别的强约束，例如”NEVER push to main””ALWAYS 在声明完成前运行 pnpm typecheck”。
  • COMMON PITFALLS（踩坑清单）：按事件累积的真实教训。vercel/vercel 的 AGENTS.md 专门收录”禁止在 CLI 包里使用 console.log”这类具体坑——把一次性教训沉淀成长期规则，这是这类文件独有的价值。

反面对照——两个经典误区：

  • 写成 README 翻版：README 回答”是什么”（给人看的营销页），AGENTS.md 回答”怎么做”（给机器看的运行手册）。Agent 不需要知道项目卖点，它需要知道”跑测试是 pnpm test 还是 npm run test:unit“。
  • 写一次就永远不改：它是活文档。Anthropic 官方的说法是：Treat it like code: review it when things go wrong, prune it regularly.

四、写法：指令式、强约束、给例子

同一条约定，两种写法的效果天差地别：

三个要点：

  1. 指令式语气：写 ALWAYS run pnpm typecheck before claiming done，不写 please check code quality。
  2. 好/坏代码对照（few-shot）：一段 Preferred/Avoid 的代码对，是上下文文件里效力最强的元素——一个具体例子胜过一千字规则描述。
  3. 小节标题用任务的自然语言命名：现代 Agent 按相关性检索文件内容，标题叫 ## Auth patterns 会在”加鉴权”任务时被命中，叫 ## 其他杂项 就永远不会。

五、组织：分层，而不是摊大饼

单一巨型文件有双重毒性：Agent 不管做什么任务都要全文处理；文件无人认领、逐渐腐化成”人人引用、没人信任”的东西。正确架构是分层 + 渐进披露：

每层继承上层的全局约定，深入本域的具体细节；Agent 按工作目录和相关性加载，天然实现了注意力配额的按需分配。主文件写 AGENTS.md（Linux Foundation 托管的开放标准，20+ 工具原生支持），Claude 专属的小众配置放 CLAUDE.md 并用一行 See @AGENTS.md 引用主文件——切换工具零成本。

加一块常被忽略但回报率很高的元信息头，防止文件悄悄腐化：

知道”谁负责、上次什么时候审过”，才知道文件过期时该找谁。

六、边界：文档只能承担 70%，红线要交给工具

一个必须接受的现实：写进 AGENTS.md 的规则，实际被遵守的比例约为 70%。 这意味着：

  • 风格类、建议类约定 → 交给文档（70% 够用，失败代价低）；
  • 安全红线、流程红线（不许 force push、不许提交未过类型检查的代码）→ 必须交给 hooks、lint、CI、提交钩子强制执行，把 30% 的漏洞用确定性工具堵死。别用 AI 当 Linter——格式交给 Prettier/ESLint，校验交给编译器和测试。

七、迭代方式：bad case 驱动，像对待代码一样对待它

不要试图一次写出完美的 AGENTS.md。最高效的路径是：

这恰好是 ACE 论文（本系列第一篇）里 Reflector-Curator 循环的人工版，也是被研究验证有效的机制：增量式 delta 更新保护既有知识的稳定性，整体重写导致上下文坍塌。

团队层面再加一条：把 AGENTS.md 纳入 Code Review。PR 改了测试框架，审查者就该问”上下文文件更新了没有”——这一条规定对长期质量的贡献超过其余所有的总和。

八、完整模板（可直接复制）

九、检查清单：你的文件是 +4% 还是 -3%

  • 每一行都能回答”没有它 AI 会犯什么错”
  • 根文件 ≤300 行，模块细节已下沉到子目录
  • 命令精确到可直接复制执行
  • 规则是指令式 + 强约束词，配有代码示例
  • 有 CRITICAL RULES 和踩坑清单两个章节
  • 有 last_updated / owner 元信息
  • 红线规则同时有 hooks/CI 强制，不只靠文档
  • 纳入 Code Review，bad case 驱动增量更新

PostgreSQL 实战手册（五）：事务、MVCC 与锁

系列收官篇。前面四篇是”怎么用”，这篇是”为什么”——事务、MVCC、锁是 PG 所有行为的地基。延续 shop 演示库，基于 PostgreSQL 16。

系列目录：一、基础命令与日常管理 ｜ 二、函数与存储过程 ｜ 三、视图与常用函数精讲 ｜ 四、性能分析与 SQL 调优 ｜ 五、事务、MVCC 与锁

一、事务基础

PG 事务的两个 MySQL 用户会惊喜的特性：

  1. DDL 可回滚：BEGIN; ALTER TABLE ...; ROLLBACK; 表结构原样恢复。线上变更可以先包事务试跑。MySQL 的 DDL 隐式提交，做不到
  2. 保存点（SAVEPOINT）是真子事务：可以嵌套使用、可以只回滚一段。代价是子事务有额外开销，循环里高频建保存点是性能杀手（第二篇的 EXCEPTION 块开销来源就是它）

二、隔离级别：名字相同，语义不同

级别 PG 16 的真实语义 MySQL InnoDB 对照
READ UNCOMMITTED 存在但没有脏读——实际表现得和 READ COMMITTED 一样 真会读到未提交数据
READ COMMITTED（默认） 每条语句取一个新快照 同名，语义接近
REPEATABLE READ 整个事务一个快照；且没有幻读（快照隔离天然免疫） 靠 next-key 锁防幻读，语义不同
SERIALIZABLE 快照隔离 + SSI 谓词锁检测，发现危险结构直接报错回滚 实质退化为加锁读

两个必须记住的推论：

  • PG 的 REPEATABLE READ 比 MySQL 的同名级别更强（无幻读），MySQL 默认 RR 而 PG 默认 RC，跨数据库迁移时隔离级别映射不能按名字抄
  • SERIALIZABLE 是有重试义务的：PG 检测出序列化冲突会抛 SQLSTATE 40001 (serialization_failure)，应用必须捕获并重试整个事务。不重试的应用没资格用这个级别

三、MVCC：xmin 和 xmax 说透

PG 的 MVCC 没有 undo log，机制与 InnoDB 截然不同：

每一行（元组）物理上携带两个系统列：xmin（创建它的事务 ID）和 xmax（删除/更新它的事务 ID）。

  • INSERT：写入新元组，xmin = 当前事务
  • DELETE：不删数据，只把 xmax 标记为当前事务
  • UPDATE = DELETE + INSERT：旧元组标 xmax，新元组带新 xmin 追加到表尾

查询时，每个事务拿一个快照（当前活跃事务清单），逐行判断”这个版本的 xmin 在我快照里是否已提交、xmax 是否还没生效”，决定该行对”我”是否可见。

与 InnoDB 的机制差异（面试与运维都高频）

InnoDB PostgreSQL
旧版本存哪 undo log（集中存储） 就在表本体里（就地多版本）
UPDATE 成本 改主键记录 + 写 undo 新版本追加，旧版本标记
回滚 应用 undo，可能很慢 直接丢弃标记即可，回滚近乎 O(1)
旧版本清理 purge 线程按 undo 清理 VACUUM 扫描表回收死元组
副作用 undo 膨胀、长事务拖累 purge 表膨胀（bloat）、事务 ID 回卷风险

PG 这套设计的直接后果：UPDATE 频繁的表会不断产生死元组，必须靠 VACUUM 回收，这是下一个主题。

四、VACUUM：PG 的”扫地僧”

4.1 它在干什么

VACUUM 扫描表，把快照里最老事务都看不见的死元组标记为可复用空间（不还操作系统，只给未来的 INSERT/UPDATE 复用）；VACUUM FULL 才重写表收缩物理文件（锁全表，慎用）。ANALYZE 常和 VACUUM 一起由 autovacuum 守护进程自动触发。

4.3 事务 ID 回卷与冻结（freeze）

PG 的事务 ID 是 32 位，约 21 亿次后会回卷。极端老的事务留下的元组必须由 VACUUM 冻结（标记为”永远可见”），否则数据库会进入只读保护模式自救。这一般只发生在长期不维护的库上，但要知道：pg_stat_user_tables 里的 age(relfrozenxid) 接近 20 亿是红色警报，需要立即 VACUUM 处理。

五、锁体系

5.1 行锁四种模式（强度递减）

模式 语义 典型场景
FOR UPDATE 最强，锁行并阻止一切修改 要 UPDATE/DELETE 这行
FOR NO KEY UPDATE 不锁外键列时的修改 PG 的 UPDATE 默认用这个，减少与外键检查冲突
FOR SHARE 读共享锁，阻止别人修改 “我读的时候你不许动”
FOR KEY SHARE 最弱，只挡主键修改 外键引用检查内部使用

5.2 SKIP LOCKED：一条 SQL 实现无锁竞争队列

这是 PG 最实用的并发武器，任务队列/抢单场景标配：

已被其他事务锁住的行直接跳过，不排队、不死锁。MySQL 8.0 也加了同样的语法（FOR UPDATE SKIP LOCKED），语义一致。

5.3 表锁：看懂模式名就够

日常只需要知道三档：ACCESS SHARE（普通 SELECT）、ROW EXCLUSIVE（DML）、ACCESS EXCLUSIVE（ALTER TABLE、VACUUM FULL——挡住一切，所以大表 DDL 才是高危操作，可用 CREATE INDEX CONCURRENTLY、pg_repack 这类工具规避）。

5.4 咨询锁：应用层的分布式锁

不锁任何行，纯粹按一个 64 位整数互斥——在”不能依赖 Redis”的环境下，这是现成可靠的分布式锁。

七、避坑指南：事务的五个高发病

  1. 长事务是万恶之源：它钉住快照，让全库的死元组无法被 VACUUM 回收，表越胀查询越慢——监控 pg_stat_activity 里 state = 'active' 且 xact_start 很老的会话
  2. idle in transaction 同样致命：事务挂着不动（常见于应用忘了 commit/连接泄漏），危害等同长事务，设置 idle_in_transaction_session_timeout 兜底
  3. READ COMMITTED 下的”读-改-写”不等于原子：读出来在应用层算完再写回，中间别人已改过——用第五节的 FOR UPDATE 或解法 C
  4. SERIALIZABLE 不重试就别用：40001 是正常控制流，不是故障
  5. 大表 ALTER TABLE 的 ACCESS EXCLUSIVE 锁会瞬间堆起等待队列，高峰期做 DDL 等于自杀——CREATE INDEX CONCURRENTLY、分批加列、低峰窗口是基本素养

总结

  • DDL 可回滚、保存点可嵌套；但保存点是子事务，别在热循环里造
  • PG 默认 READ COMMITTED；REPEATABLE READ 是快照隔离（无幻读），与 MySQL 同名不同实
  • MVCC 机制：元组带 xmin/xmax，UPDATE = 删旧加新，回滚近乎 O(1)，代价是死元组靠 VACUUM 回收
  • 盯死三个监控：n_dead_tup 比例、长事务/idle in transaction、age(relfrozenxid)
  • 行锁四模式按需取用；队列场景记住 FOR UPDATE SKIP LOCKED；分布式互斥用 pg_advisory_xact_lock
  • 丢失更新优先用”数据库内计算”解法（SET stock = stock - 1 WHERE stock >= 1），其次悲观锁，乐观锁兜底

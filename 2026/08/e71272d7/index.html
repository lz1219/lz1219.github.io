上下文工程（一）：为什么"塞更多"正在失效——从 Context Rot 到自我进化的 Playbook

发表于2026-08-14|更新于2026-08-14|技术
|浏览量:

2025 年 7 月，Chroma 用 18 个前沿模型做了一组实验，得出的结论让整个行业沉默了：所有模型——无一例外——都会随着输入变长而退化。 厂商宣传的”百万 token 上下文窗口”是容量，不是可用容量。承认这一点之后，一门新学科正式登上舞台：上下文工程（Context Engineering）。本文系统梳理 2025–2026 年这个领域最重要的研究和最实用的工程解法，作为本系列的开篇。

一、一个价值连城的误会：”窗口更大 = 能力更强”

过去三年，上下文窗口从 4K 膨胀到 1M token，”大海捞针”（Needle in a Haystack）测试里各家模型动辄接近满分。于是一个危险的假设流行开来：既然装得下，那就全塞进去。

Chroma 在 2025 年 7 月发布的技术报告 Context Rot: How Increasing Input Tokens Impacts LLM Performance 打碎了这个假设。他们的实验设计堪称教科书级别：任务本身保持不变，只改变输入长度，然后在 Claude 4 系列、GPT-4.1 系列、Gemini 2.5 系列、Qwen3 系列共 18 个前沿模型上复现。

结论有三层，一层比一层扎心：

  1. 全部 18 个模型都随输入变长而退化——不是大多数，是全部。一个在 5K token 下满分的任务，到 100K token 时可能明显下滑，远未触及窗口上限。
  2. 退化是长度驱动的，不是位置驱动的。此前 Stanford 的”Lost in the Middle”（2023）认为信息放在上下文中间会被忽视，但 Chroma 在实验中把关键信息放在各个位置测试，没有发现稳定的位置优势——“把重要内容放开头或结尾”这条流传甚广的经验，并不可靠。
  3. 干扰项（distractors）是隐形杀手。当上下文中混入与正确答案语义相似但不正确的内容时（真实代码库里到处都是这种东西），性能随长度和干扰项数量双重下滑。

更深一层的警告是：”大海捞针”测试之所以失效，是因为它只考词汇匹配——问题里的词和答案里的词高度重叠。而真实任务是语义匹配：你问”我们海外扩张进展如何”，模型要自己把”海外扩张”关联到具体国家和营收数字。正是这类任务，在长上下文下退化最严重。

百万 token 窗口是图书馆的建筑面积，不是你的工作台。 这就是 Context Rot（上下文腐化），也是上下文工程存在的理由。

二、四种死法：长上下文失败模式分类学

如果说 Context Rot 回答了”会退化”，那么 Drew Breunig 在 2025 年 6 月总结的四大失败模式回答了”怎么退化”。这套分类学已经成为业界通用语言：

失败模式 机理 真实案例
Context Poisoning（中毒） 一条幻觉/错误信息进入上下文，被后续反复引用、不断自我强化 DeepMind 的 Gemini 2.5 宝可梦 Agent：上下文超过 10 万 token 后，目标区被污染，开始追逐不可能完成的目标
Context Distraction（分心） 历史太长，模型过度依赖”以前做过什么”，重复旧动作而不是重新推理 Agent 在长会话里机械重复已失败的工具调用
Context Confusion（迷惑） 多余内容稀释注意力；工具过多时尤其明显 研究观察到工具超过约 20 个时，部分模型的工具选择开始漂移
Context Clash（冲突） 后续信息与先前上下文矛盾，模型被撕裂 Laban 等人的研究发现多轮对话中性能下降 39%，主要归因于此

工程侧还有一个 2026 年的压缩研究综述（arXiv 2605.2065）补充了针对”压缩”这一解法本身的三级失败：F1 压缩时机决策错误、F2 压缩过程信息丢失、F3 压缩后无法找回原文。你用来救上下文的手段，本身就是新的失败来源——这点后面会再讲到。

三、工程解法四大件：目前生产环境验证过的全部家当

Anthropic 在 2025 年 9 月的工程博客 Effective Context Engineering for AI Agents 中给出了经过生产验证的核心原则：”找到最小的高信号 token 集合，最大化期望结果的概率。”围绕这个原则，四种解法已经被主流 Agent 产品广泛采用：

3.1 压缩（Compaction）

定期把历史总结成摘要，用摘要重启上下文。代价是细节丢失换取续航。

  • 最常见的坑：压缩不当会导致”thrashing”——Agent 因为摘要丢了关键信息，被迫重新读文件、重跑工具，来回打转。
  • 最轻量的变体：只清理陈旧工具结果（tool result clearing），保留消息结构。Anthropic 的产品化版本（context editing）在 100 轮网页搜索评测中，让原本会耗尽上下文的任务顺利完成，同时减少 84% 的 token 消耗。
  • 2026 年的新趋势：服务端压缩（Anthropic compact-2026-01-12），由 API 侧保证 tool_use/tool_result 配对完整性，避免本地压缩产生的孤儿引用把会话弄崩。

3.2 结构化笔记 / 外部记忆（Structured Note-taking）

让 Agent 把工作状态写到上下文之外的文件里（NOTES.md、todo 清单、决策日志），需要时再读回来。Anthropic 的 memory tool 给模型提供对 /memories 目录的文件操作能力，结合 context editing 后，agentic search 性能提升 39%。Claude Code 的 CLAUDE.md、各类 Agent 的 AGENTS.md，本质上都是这个思想的产物：记忆放在文件系统里，工作上下文保持精简。

3.3 子代理隔离（Sub-agent Isolation）

主代理只持有高层计划，把脏活累活派给拥有干净独立窗口的子代理；子代理烧掉几万 token 探索后，只返回一份 1000~2000 token 的蒸馏摘要。

效果有多猛？Anthropic 的多代理研究系统（Opus 4 主代理 + Sonnet 4 子代理）在内部研究评测上比单代理 Opus 4 高出 90.2%。

但请记下一个重要的反面边界：Anthropic 自己明确指出，多代理不适合子任务之间需要大量共享上下文、互相依赖紧密的场景——比如写代码。它适合广度优先的研究类任务，不适合深度耦合的工程任务。代价也不低：token 消耗约为普通对话的 15 倍。

3.4 即时检索（Just-in-Time Retrieval）

这是数据获取范式的根本转移：从预加载（预先把资料塞进上下文）转向用时再取。

  • 传指针，不传内容：上下文里只放文件路径、ID、URL，Agent 需要时自己调工具取详情；
  • 渐进披露（Progressive Disclosure）：先给摘要，Agent 逐层下钻——文件列表 → 元数据 → 正文。Claude 的 Skills 系统就是这个机制的工程实现；
  • 给发现工具，不给数据倾倒：提供 search_docs() + read_doc()，而不是把整个知识库粘进去。

一句话总结：“别把整个图书馆寄过来，派一个图书管理员来。”

这条路线的实证支持来自 ContextBench（arXiv 2602.05892，1136 个任务、66 个仓库）：LLM 一贯偏向高召回、低精度——检索太多，用得太少。 渐进披露不是风格偏好，是被基准验证的正确姿势。

四、最前沿：上下文开始自我进化

以上是”人工程上下文”的全部武器。而 2025 年底以来，研究前沿已经推进到下一阶段：让上下文在运行中自我改进。

ACE：把上下文当成不断进化的 Playbook

Stanford、SambaNova 与 UC Berkeley 的 ACE（Agentic Context Engineering，arXiv 2510.04618，ICLR 2026）是目前这条线上最重要的工作。它先诊断出传统上下文优化的两个慢性病：

  • 简洁偏见（Brevity Bias）：优化器倾向于把上下文压缩成简短通用的总结，领域细节被丢弃；
  • 上下文坍塌（Context Collapse）：每轮迭代都整体重写上下文，细节在多轮重写中被逐步侵蚀——和文档腐化一模一样的病，只是发生在机器手里。

ACE 的处方是把上下文视为一本持续积累、逐条修订的 Playbook（战术手册），由三个角色维护：

关键设计是增量式 delta 更新：绝不整体重写，只局部增补和修订——这直接杀死了上下文坍塌。效果：AppWorld 智能体基准上 +10.6%（最高 +17.1%），金融推理基准 +8.6%，适配延迟降低 86.9%，而且不需要人工标注，只靠执行反馈（代码跑没跑通、任务成没成功）就能自我进化。论文中最有象征意义的结果：一个较小的开源模型（DeepSeek-V3.1）+ ACE，打平了榜单上基于 GPT-4.1 的顶级生产级 Agent。

上下文工程由此从”运维规范”升格为”训练机制”——不改模型权重，只改输入，就能让系统持续变强。

其他值得盯紧的前沿方向

  • Context-Folding（arXiv 2510.11967）：把”开子任务 → 折叠只留结论”做成模型原生动作（branch/return），配合强化学习训练，在深度研究和 SWE 任务上以约 1/10 的活动上下文匹配甚至超过 ReAct。
  • 观察掩码（Observation Masking，JetBrains，NeurIPS DL4C 2025）：简单到令人不安——只是把无关信息遮掉，性能 +2.6%，成本 -52%。再次印证”更少、更准 > 更多”。
  • 文件系统即外存：2026 年的研究（Coding Agents are Effective Long-Context Processors）论证了编码 Agent 把代码库文件系统当作”外挂上下文窗口”使用的有效性——你不需要把代码放进上下文，你需要让 Agent 随时找得到。
  • 上下文压缩的系统化：2026 年 5 月的综述（arXiv 2605.2065）首次统一了压缩对象、压缩机制、触发策略三个设计维度，并整理了 F1/F2/F3 失败分类——这个子领域正在从手艺变成工程学科。

五、一盆必要的冷水：AGENTS.md 可能正在帮倒忙

2026 年 2 月，ETH Zurich 的 Evaluating AGENTS.md（arXiv 2602.11988）在 SWE-bench Lite 和新基准 AGENTbench 上做了 438 个任务的对照实验，结果让很多人都该重新审视自己的仓库：

  • LLM 自动生成的上下文文件，使任务成功率下降约 3%；
  • 人工精心编写的文件，提升约 4%；
  • 两者都让推理成本上升超过 20%。

结论：上下文文件不是”有比没有好”，而是**”准比有重要”**。自动生成的泛泛文件是噪声源；只有包含精确的构建命令、明确约束和真实踩坑记录的文件才值得存在。这与 Chroma 的干扰项实验、JetBrains 的掩码实验指向同一个方向：

上下文工程的守恒定律：每一个低质量 token，都在消耗高质量 token 的注意力配额。

六、落地清单：现在就能做的事

把上面的研究翻译成个人开发者和团队的行动项：

会话层面（今天就能改）

  1. 长会话感觉到输出质量下滑时，主动重开会话 + 携带摘要，而不是硬撑；
  2. 上下文中只放路径和指针，让 Agent 自己读文件——相信它的 grep；
  3. 工具/技能别贪多，超过 20 个就该做减法；
  4. 警惕”中毒”：发现 Agent 反复引用一个错误结论时，立刻纠正或重开，错误在上下文里会自我繁殖。

仓库层面（本周就能做）

  1. AGENTS.md 坚持手写、保持精简（社区共识：根文件 300 行以内），只写”没有它 AI 就会犯错”的内容；
  2. 每个模块级细节下沉到子目录文档，避免单一巨型文件；
  3. 用 lint、测试、CI 把红线变成自动化检查，别指望文档的 70% 遵守率；
  4. 维护”踩坑清单”：AI 每犯一次错，补一条针对性规则——这正是 ACE 的 Reflector-Curator 循环的人工版，也是被论文验证有效的机制。

架构层面（构建 Agent 系统时）

  1. 长任务优先结构化笔记（外部记忆），其次压缩，谨慎使用多代理——先想清楚子任务间是否深度耦合；
  2. 检索链路按”两段式”搭建：先粗筛到几百条，再用 LLM 精排；
  3. 给压缩策略留出”找回原文”的逃生通道（记住 F3 失败：压缩后无法访问原文）。

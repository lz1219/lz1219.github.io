上下文工程（四）：多代理与子代理——什么时候该拆，什么时候是给自己挖坑

发表于2026-08-14|更新于2026-08-14|技术
|浏览量:

2025 年 6 月，”上下文工程”一词的提出者、Cognition 联创 Walden Yan 发文《Don’t Build Multi-Agents》，公开唱反调：OpenAI Swarm、Microsoft AutoGen 推崇的多代理架构是”构建 Agent 的错误方向”。同一时期，Anthropic 的多代理研究系统却拿出了比单代理高 90.2% 的成绩。谁对？都对——而且分歧点恰好是这个领域最有价值的知识。 本文给出完整的裁决。

一、Cognition 的反对：两条不可违反的原则

Walden Yan 的论证建立在他从构建 Devin（AI 软件工程师）中提炼的两条原则上：

原则 1：共享上下文，且要共享完整的行动轨迹（full traces），不只是单条消息。

原则 2：行动携带隐含决策，冲突的决策导致坏结果。

他用克隆 Flappy Bird 的例子演示：把任务拆给两个子代理，一个做鸟、一个做背景——两个子代理互相看不见对方在做什么，各自基于未被事先约定的假设做决策，结果鸟和背景是两种完全不搭的视觉风格。

这就是多代理的核心病灶：每个动作都隐含一连串决策（配色、风格、接口约定、错误处理方式），而这些决策从未被显式沟通。 人类工程师遇到冲突会”聊一聊达成共识”，但 2025 年的模型之间还不具备这种高效的长上下文主动协商能力。Yan 的结论是硬的：

“原则 1 和 2 如此关键、如此不值得违反，你应该默认排除一切不遵守它们的架构。”

按这两条原则，最稳妥的架构是单线程线性 Agent——上下文连续、决策一致。超长任务的续航问题，用一个专门的压缩模型把历史行动压缩成关键细节、事件和决策来解决（Cognition 内部甚至为此微调了小模型）。

二、Anthropic 的反证：+90.2% 从哪来

Anthropic 的多代理研究系统（Opus 4 主代理 + Sonnet 4 子代理并行）在内部研究评测上比单代理 Opus 4 高出 90.2%。性能差异的 95% 可由三个因素解释：token 使用量（约解释 80%）、工具调用次数、模型选择。

但这份成绩单附带了明确的适用边界，Anthropic 自己写得非常清楚：

  • 适合：广度优先的任务——研究、搜索、并行探索大量独立方向（”同时调查 20 个子话题”）；
  • 不适合：子代理间必须共享大量上下文、互相依赖紧密的任务——编码被直接点名为多代理的糟糕适用场景；
  • 代价：token 消耗约为普通对话的 15 倍——没有足够高价值的任务，经济上就不成立。

两者说的是同一个原则的两个侧面：决策权不能分散，但上下文消耗可以分摊。

三、2026 年的最新进展：风向变了多少

值得更新的是，Yan 本人在 2026 年 4 月修正了自己的表述：

“一年前我会告诉大家别建多代理，专注上下文工程基本功。今天，很多诱人的想法仍然不实用，但我们已经找到了一些真正有效的配置。“

背景是 2025 年 12 月的模型能力拐点（Opus 4.5、GPT-5.2 级别）之后，”从规格说明直接产出 PR”成为现实工作流，行业进入异步 Agent 时代——Devin 在 Cognition 自家仓库的提交占比从 2026 年 1 月的 16% 升到 3 月的 80%，PR 使用量增长 7 倍。多代理编排从”脆弱的玩具”变成”有条件可用的基础设施”，但前提条件没变：有效的配置依然建立在上下文工程基本功之上。

学术侧也有呼应：LOCA-bench（2026）证明性能随环境复杂度上升而下降；AgentTracer 这类工作专门研究”多代理系统中到底是谁引入了失败”——故障归因在分布式 Agent 中至今是难题。

四、子代理的正确打开方式：要”隔离”，不要”协作”

目前被生产环境反复验证的多代理用法，只有一个稳定形态——编排者-工作者（Orchestrator-Workers），而且要点在于把它当上下文隔离机制用，而不是当”团队协作”用：

三个纪律：

  1. 决策权唯一：子代理只做信息收集和明确的执行任务，不做影响全局的决策；
  2. 接口即摘要：父子之间只传”输入任务 → 蒸馏结论”，中间过程用完即弃——这正是第一篇讲的子代理隔离；
  3. 并行要赚回成本：子任务必须是真正独立的（查不同文档、测不同模块、评估不同方案），否则 15 倍的 token 消耗就是纯浪费。

前沿研究正在把这个模式做成模型原生能力：Context-Folding（arXiv 2510.11967）让模型学会主动”开分支执行子任务、折叠只留结论”，在深度研究和 SWE 任务上以约 1/10 的活动上下文匹配甚至超过 ReAct。可以理解为：单代理学会了在自己的上下文里”内部开子代理”。

五、决策框架：拆，还是不拆

动手拆之前，按顺序过这五问：

# 问题 倾向于
1 子任务之间是否需要共享大量中间状态或决策？ 是 → 别拆（单线程 + 压缩）
2 任务是广度优先（并行探索独立方向）还是深度优先（链式依赖）？ 深度 → 别拆
3 子任务能否定义清晰的输入/输出接口？ 不能 → 别拆
4 单代理是否真的会撑爆上下文或拖慢关键路径？ 不会 → 别拆（别为架构而架构）
5 任务价值是否撑得起数倍到 15 倍的 token 成本？ 撑不起 → 别拆

五个问题里只要有一个指向”别拆”，就先用单线程线性 Agent + 压缩/笔记机制——Yan 的原话是”这个简单架构能带你走得出乎意料地远”。

适合拆的典型：多方向调研、大规模代码库的并行审查（按模块划分）、多候选方案并行评估、独立测试矩阵。
不该拆的典型：同一个功能的设计+实现（决策深度耦合）、调试单个复杂 bug（线索链式依赖）、任何”子代理需要理解全局才能做对局部”的任务。

六、务实清单

  1. 默认单线程：线性 Agent + 压缩 + 结构化笔记是基准架构，先把这套做到位；
  2. 第一个子代理只用于”读”：信息检索/探索类子代理最安全——它不写代码，就没有决策冲突；
  3. 摘要预算写进系统：子代理返回值强制控制在 1~2K token；
  4. 共享上下文用制品（artifacts），不用对话：子代理产出写入文件，主代理读文件——文件是天然的完整轨迹；
  5. 监控成本：多代理上线第一天就配 token 计量，15 倍消耗不应该是个惊喜；
  6. 永远能归因：保留各子代理的完整轨迹日志——分布式系统的故障归因难题，靠日志而不是靠运气。

七、系列结语

四篇下来，上下文工程的完整地图已经清晰：

  • （一） 问题侧：Context Rot 证明”塞更多”失效，四大失败模式定义了战场；
  • （二） 静态层：AGENTS.md 把项目知识写成 Agent 可消化的形态（+4% 与 -3% 的分水岭）；
  • （三） 时间层：记忆系统让经验跨会话存活，写入侧纪律决定它是资产还是负债；
  • （四） 空间层：多代理把上下文消耗分摊到独立窗口，但决策权必须集中。

四层共用同一个内核，也是 Walden Yan 那句定义的另一面：上下文工程是在动态系统中自动完成”让模型在正确的时间看到正确的信息”这件事。 模型会继续变强，窗口会继续变大，但只要注意力和成本仍然有限，这门手艺就仍然值钱。

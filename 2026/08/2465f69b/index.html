与 AI 的第一次对话：新建项目与已有项目的上下文策略

发表于2026-08-14|更新于2026-08-14|技术
|浏览量:

与 AI 协作的效率，往往不取决于你问得多聪明，而取决于你在第一次对话时给了它多少正确的上下文。

随着 Claude Code、Cursor Composer、Kimi Work 等 AI 编码智能体的普及，”打开项目 → 直接开始对话”成了很多开发者的下意识动作。但这种做法在新项目和已有项目上的效果差异极大。本文结合实际协作经验，梳理两种场景下第一次对话应关注的核心策略。

一、为什么”第一次对话”如此关键

AI 智能体的工作方式与人类实习生类似：它没有关于你项目的长期记忆（除非项目本身内置了记忆系统），每一次对话窗口都是一次”重新上岗”。第一次对话传递的信息质量，直接决定了后续产出的相关性和准确性。

常见的问题模式是：

  • 信息过少：只丢一句”帮我写个登录功能”，AI 只能基于通用假设生成代码，大概率与你的技术栈不匹配。
  • 信息过载：一次性粘贴 5000 行代码和 10 个需求文档，AI 的上下文窗口被噪声淹没，反而抓不住重点。
  • 假设偏差：你以为 AI “应该知道” 你的项目结构，但实际上它对 src/ 和 app/ 的理解完全取决于你的说明。

好的第一次对话，核心目标是建立共享上下文（Shared Context）——让 AI 在认知上与你的项目对齐。

二、新建项目：从零定义规则

新建项目的第一次对话，本质是架构决策与规范约定的过程。此时没有既有代码的约束，AI 的输出自由度很高，但也更容易偏离你的预期。

2.1 必须明确的信息

（1）技术栈与版本

不要只说”用 React”，要说”React 18 + TypeScript + Vite + React Router v6”。版本差异会导致 API 完全不同（如 React 18 的 Concurrent Features、React Router v6 的 <Outlet> 模式）。

（2）项目目标与范围

AI 需要理解”为什么做”，而不仅是”做什么”。

  • 差：写一个博客系统
  • 好：一个个人技术博客，面向中文读者，需要 SEO 友好，支持 Markdown 渲染，评论系统用 giscus，部署到 GitHub Pages

后者让 AI 在决策时会自动考虑静态生成、i18n、CDN 等约束。

（3）目录结构与命名规范

如果你期望 components/ 按功能域组织（features/auth/LoginForm.tsx），而不是按类型组织（components/forms/LoginForm.tsx），必须在第一次对话时说明。否则 AI 会按最常见的惯例生成，后续重构成本很高。

（4）非功能性需求

  • 性能要求（如首屏加载 < 1s）
  • 浏览器兼容性（是否支持 IE11）
  • 代码质量要求（是否需要单元测试覆盖率 > 80%）
  • 安全约束（是否处理敏感数据，是否需要 CSP）

三、已有项目：先对齐现状，再谈变更

已有项目的第一次对话，核心挑战是让 AI 快速理解现有代码库。此时 AI 的输出必须与既有代码兼容，而不是另起炉灶。

四、两种场景通用的核心原则

无论新建还是已有项目，以下原则始终适用：

4.1 上下文分层传递

不要试图在一条消息中说清所有事情。将信息分层：

  1. 层 1 - 背景：项目是什么、用什么技术、目标是什么
  2. 层 2 - 现状：当前做到了哪一步、遇到了什么问题
  3. 层 3 - 任务：本次对话具体要做什么
  4. 层 4 - 约束：不能做什么、必须遵循什么规范

4.2 使用参考文件（Reference Files）

如果项目根目录有 AGENTS.md、CONTRIBUTING.md、ARCHITECTURE.md 等文档，在第一次对话时主动引用。这些文档是”给 AI 看的项目说明书”，能大幅减少沟通成本。

4.3 确认理解再执行

在让 AI 生成代码之前，先让它用自己的话复述一下需求和约束。例如：

“在正式开始之前，能否总结一下：1）这个项目的核心目标；2）你理解的技术栈；3）本次任务的具体要求；4）需要遵守的约束。”

这个步骤能捕获 80% 的误解。

4.4 迭代优于一步到位

AI 擅长在明确的、小范围的任务上表现出色。将大任务拆分为多轮对话，每轮聚焦一个子任务，远比一次性要求”帮我写完整个系统”更有效。

五、写在最后

与 AI 的第一次对话，本质上是一次知识转移的过程。你的目标不是”问一个问题”，而是在短时间内把一个陌生人（AI）培养成能理解你项目的协作者。

  • 新建项目时，你是架构师，需要定义规则；
  • 已有项目时，你是导游，需要带它快速熟悉地形。

两种角色都需要主动管理上下文，而不是假设 AI “应该知道”。当你开始把 AI 当作一个需要 onboarding 的新团队成员，而不是一个无所不知的 oracle 时，协作效率会有质的提升。

推荐阅读

如果你想深入了解如何为 AI 编写项目说明文档，可以搜索 “AI-friendly project documentation” 或 “Context Engineering for LLMs”。这是比 Prompt Engineering 更高阶的能力——不是优化一句话，而是优化整个项目的知识组织方式。

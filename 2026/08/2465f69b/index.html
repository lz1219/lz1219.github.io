与 AI 的第一次对话：新建项目与已有项目的上下文策略

发表于2026-08-14|更新于2026-08-14|技术
|浏览量:

大多数”如何给 AI 上下文”的文章都在回答错误的问题。它们教你给什么，但真正决定成败的是你把上下文放在哪一层——对话里、文档里、代码结构里，还是自动化检查里。这四层的可靠性天差地别，而第一次对话的真正价值，就是为每一条重要信息选择正确的归宿。

一、一个被忽视的模型：上下文的四个层级

先摆几个有出处的硬事实，它们构成了本文全部策略的地基：

  • 前沿模型能稳定遵循的指令总量大约只有 150~200 条，超过之后遵守率快速衰减（Anthropic 及社区多组实验的共识）。
  • 写进 CLAUDE.md / AGENTS.md 的规则，实际被遵守的比例大约是 70%——剩下 30% 的漏洞，靠文档永远堵不上。
  • LLM 有明确的位置偏见：它高度关注上下文的开头和结尾，夹在中间的长文档容易沦为”被遗忘的中间层”。
  • Anthropic 工程博客对上下文的总原则只有一句话：informative, yet tight（信息充分，但要紧凑）。

把这四条拼起来，会得到一个反直觉的结论：上下文给得越多，效果可能越差。 真正的问题是安置问题。按照可靠性从低到高，上下文有四个层级：

层级 载体 可靠性 失效方式
L1 对话中口头说 一次性，会话结束即消失 位置偏见、会话中断、新会话遗忘
L2 AGENTS.md 等项目文档 持久，约 70% 被遵守 指令超量后衰减、文档腐化过期
L3 代码结构本身（命名、目录、既有模式） 很高——AI 通过 grep 和模仿既有代码遵循 结构本身混乱
L4 自动化检查（lint、测试、类型检查、hooks） 100% 强制，不依赖模型自觉 无（除非你没写这条检查）

注意 L3 层，它最常被忽视也最值得展开。现在的编码 Agent 最核心的能力是 grep——它会主动搜索你的代码库。这意味着：如果每个概念在你的代码里都有一个独特、一致、可搜索的名字，AI 自己就能找到所有需要改的地方，根本不用你教。 同样，AI 模仿既有代码模式的能力，远强于遵守抽象规则。你的代码库本身就是最好的上下文，前提是你把它写得”可读、可搜、可模仿”。

第一次对话的核心动作因此变成了：每给出一条重要信息，都问自己一句——它应该住在哪一层？

  • “这次任务要改登录模块” → L1，对话里说就够了；
  • “本项目错误处理统一用 Result 类型” → L2，写进 AGENTS.md；
  • “订单模块的目录按领域划分” → L3，落实在目录和命名里；
  • “禁止提交未通过类型检查的代码” → L4，交给 CI 和提交钩子，别指望 AI 自觉。

二、新建项目：第一次对话要完成的三件事

新建项目时 AI 自由度最高，跑偏的代价也最大。第一次对话不是”提需求”，而是完成三件事。

2.1 定契约：要选项，不要答案

新项目的选型决策一旦由 AI 默认拍板，后面全是沉没成本。正确的打开方式：

三个要点：说”为什么做”而不只是”做什么”（”SEO 友好、无后台”直接决定了静态生成方案）；要候选方案而非单一答案（AI 默认选它最熟的，不是最合适的）；动手前让它复述（一分钟成本，拦截方向性误解）。

2.2 立骨架：Plan 先行，代码后行

业界沉淀下来的标准节奏是 探索 → 计划 → 编码 → 验证，而不是一句话直接要代码。方案是一页纸，改起来一句话的事；代码是几百行，改架构等于推倒重来。第一轮要方案，第二轮审方案，第三轮才生成骨架和工程化配置（lint、格式化、类型检查、CI）——这些配置就是 L4 层的雏形，必须在第一天就位。

2.3 分层落地：这是新项目独有的红利

新项目第一次对话产出的所有决策，当天就要按层级固化：

  • 全局约定、构建命令、红线规则 → 写进根目录 AGENTS.md（控制在 300 行以内，HumanLayer 生产环境只有 60 行——每写一行都问一句：没有这句，AI 真的干不了活吗？）；
  • 模块级细节 → 写进对应子目录的文档，而不是全堆在根文件里（分层结构让 AI 按任务相关性加载，避免指令超量）；
  • 目录组织和命名规范 → 直接体现在骨架代码里，让”可 grep 的一致性命名”从第一天就是现实；
  • “必须过测试””禁止某类操作” → 变成 lint 规则、CI 步骤和 hooks，而不是口头约定。

反过来说，新项目最不该做的是把 AGENTS.md 当成万能的。文档只承担 70%，剩下 30% 要交给结构和工具。

三、已有项目：关键不是”喂”，而是”指路 + 验收”

已有项目的矛盾是：AI 对代码库一无所知，而改动必须与既有代码严丝合缝。这里第一次对话的策略和新项目完全不同——重点不是灌输信息，而是建立两条通道：一条让 AI 自己找到路，一条让你能验证它走对了。

3.1 喂地图，不喂代码

不要倾倒代码，给一张标注过的地图：

注释才是地图的灵魂：”改任何接口前先看这里””所有请求都经过”——这类话直接标出了代码库的承重墙。花两分钟写地图，省掉 AI 十轮无效探索。

3.2 动手之前，先让它”追踪一条链路”

对齐已有项目理解的最有效方法，不是让 AI 读一堆文件，而是让它端到端追踪一条真实业务流程（比如”一次登录从路由到数据库的完整路径”），并且：

  • 每个结论都要引用具体文件作为依据——区分”代码支持的结论”和”它的猜测”；
  • 主动列出不确定项——“哪些地方你不确定？需要看哪个文件或问谁来确认？”

这一步同时完成了两件事：AI 建立了对工作区域的准确认知，你也看到了它理解的对不对。理解有偏差，在这里纠正只要一句话；等代码写完再发现，就是一次返工。

3.3 任务描述三要素：位置、预期 vs 实际、验收命令

  • ❌ 帮我看看登录好像有点问题
  • ✅ OAuth 登录回调有问题。相关代码在 src/app/api/auth/route.ts（NextAuth.js）。预期：登录成功重定向到 /dashboard；实际：302 循环。我已排除：回调 URL 配置无误。验收标准：npm run test:auth 全绿 + 手动走一遍登录流程成功。

“验收命令”是最容易被忽略、也最值钱的一项。它把”做完没有”的判断从 AI 的自我感觉，变成了可执行的客观检查——这正是 L4 层思想在对话中的体现。Anthropic 的最佳实践反复强调：给 Agent 一个能自己运行的验证手段（测试、构建、截图对比），它的输出质量会有台阶式的提升，因为它可以自己纠错，而不是等你发现。

3.4 风格不给规则，给例子

“错误处理要规范、日志要打全”这类抽象规则，语义上接近一切、指导不了任何具体决策。有效的做法是指定一个参照文件：

“新增代码的错误处理与日志风格，严格模仿 src/services/order.ts。”

这就是 few-shot 的力量：一个具体例子胜过一千字的规则描述。同理，改动前要求影响面分析——“先列出哪些文件和调用方可能受影响，再动手”——已有项目最大的风险从来不是改不对，而是改对了 A、改坏了依赖 A 的 B。

四、通用反模式清单（带”为什么”）

反模式 为什么会失败 正确姿势
在对话里口头立规矩 会话结束即失效，下轮全部重来 重要约定当场写入 AGENTS.md 或配置
AGENTS.md 写成万字长文 指令超 150~200 条后遵守率骤降，中间部分被位置偏见淹没 根文件 ≤300 行，细节下沉到子目录文档
写”代码要整洁”式规则 语义太泛，匹配一切即指导不了任何决策 给出好/坏两段代码的对比例子
一股脑贴几千行代码 噪声淹没重点，被稀释的重点等于没给 喂地图 + 按需展开，让 AI 自己 grep
一句话需求直接要代码 AI 用”平均惯例”填补你没说的部分 先方案后代码，关键决策人工确认
不给验收标准 AI 用自我感觉判断”完成”，你只能人工兜底 附上可执行的验收命令（测试/构建/脚本）
指望 AI 自觉遵守红线 文档规则遵守率只有约 70% 红线交给 hooks、CI、lint 强制执行
上下文文件写完就不管 文档腐化后比没有更糟（AI 学到过期约定） 像对待代码一样对待它：出问题就审查，定期修剪

最后一条值得单独强调：上下文文档是活资产，不是一次性交付物。 最高效的维护方式是 bad case 驱动——AI 每犯一个错，就问自己”如果文档里多写哪一条，它就不会再犯”，然后只补那一条。增量维护，而不是定期重写。

六、写在最后

回到开头那个模型。与 AI 协作的第一次对话，表面上是”给信息”，实质上是一次上下文的分层安置：

  • 一次性的任务信息，留在对话里，说清位置、预期和验收；
  • 需要长期遵守的约定，写进文档，并且保持紧凑到 AI 能真的遵守；
  • 项目的架构和命名，做成”可搜索、可模仿”的代码现实，让 AI 自己找路；
  • 不能让步的红线，交给自动化检查，不赌那 70%。

新建项目时，你手中有把这个体系一次建对的红利；已有项目时，你的价值在于指路和验收，而不是搬运信息。两种场景殊途同归：把 AI 当一个需要 onboarding 的新同事——入职文档要短而准，工位（代码库）要整洁可辨，门禁（自动化检查）要装在第一道门上。

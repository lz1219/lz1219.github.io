MySQL 实战手册（三）：视图与常用函数精讲

系列第三篇。视图是封装复杂查询的利器，内置函数则是日常 SQL 的生产力来源——8.0 加入的窗口函数更是直接改变了报表类 SQL 的写法。沿用前两篇的 shop 库（如果你执行过第二篇的 GenOrders(10000)，现在数据量正好练手）。

一、视图：封装而不是存储

创建与使用

可更新视图与 WITH CHECK OPTION

单表、无聚合的视图可以直接 INSERT/UPDATE/DELETE，加 WITH CHECK OPTION 防止写入不满足视图条件的数据：

避坑指南：视图的三个真相

  1. 视图不存数据，也没有索引——每次查询视图都是重新执行底层 SQL。在视图上再叠视图、再套 WHERE，容易让优化器写出糟糕的执行计划（尤其 ALGORITHM=TEMPTABLE 时先全量物化再过滤）
  2. 含聚合 / DISTINCT / GROUP BY / UNION / 子查询的视图不可更新，别想当然
  3. 底层表结构变更（如删列）后视图会静默失效，查询时才报错。定期用 CHECK TABLE v_user_consumption 体检

避坑指南：日期查询的头号性能坑

同理，BETWEEN '2026-08-01' AND '2026-08-31' 查月份容易漏掉 31 号当天的数据（DATETIME 精度问题），统一用”左闭右开”区间：>= 月初 AND < 下月初。

四、聚合函数与 GROUP BY

避坑指南：聚合查询的 NULL 三兄弟

  1. COUNT(列名) 不统计 NULL，COUNT(*) 统计所有行——结果不一致时先怀疑这个
  2. = NULL 永远是 UNKNOWN：判空必须 IS NULL；更隐蔽的是 NOT IN (含 NULL 的子查询) 会返回空集，这是经典的线上 bug，用 NOT EXISTS 改写
  3. 8.0 默认开启 ONLY_FULL_GROUP_BY：SELECT 里的非聚合列必须出现在 GROUP BY 中，否则报错——别关它，它拦住的都是含糊的 SQL

五、窗口函数（8.0 重磅特性）

窗口函数在不折叠行的前提下做”组内计算”，语法：函数() OVER (PARTITION BY 分组 ORDER BY 排序)。

实战 1：每组取最新 N 条（ROW_NUMBER）

实战 2：排名（RANK / DENSE_RANK）

实战 3：环比计算（LAG / LEAD）

实战 4：累计求和（SUM OVER）

注意事项：窗口函数没法直接加索引加速，它的成本在排序上——PARTITION BY/ORDER BY 涉及的列有合适索引会明显更快；外层 WHERE rn <= 2 这种过滤发生在窗口计算之后，所以无法提前裁剪数据。

六、条件与判空函数

防除零用 NULLIF：SELECT total / NULLIF(cnt, 0) FROM t;（除数为 0 时返回 NULL 而不是报错）。

总结

  • 视图用来封装复杂 SQL、收口权限（只暴露视图不给基表），别指望它提速
  • 字符串/日期函数用在 SELECT 里随便用，用在 WHERE 的索引列上三思
  • 聚合查询盯紧 NULL 的三个坑；窗口函数优先掌握 ROW_NUMBER（每组取 N）、LAG（环比）、SUM OVER（累计）三个场景

MySQL 实战手册（三）：视图与常用函数精讲

系列第三篇。视图是封装复杂查询的利器，内置函数则是日常 SQL 的生产力来源。本篇按中级开发的标准写：每个函数给语法、给示例、给坑，JSON 函数和窗口函数这两个 8.0 的重头戏单独成章。沿用前两篇的 shop 库。

系列目录：一、基础命令与日常管理 ｜ 二、存储过程与自定义函数 ｜ 三、视图与常用函数精讲 ｜ 四、性能分析与 SQL 调优 ｜ 五、事务与锁

一、视图：封装而不是存储

创建与使用

视图的两种执行算法（决定性能走向）

创建时可显式指定 ALGORITHM=MERGE | TEMPTABLE | UNDEFINED（默认 UNDEFINED，MySQL 尽量选 MERGE）：

算法 机制 影响
MERGE 把视图 SQL 与外层查询合并改写后执行 外层的 WHERE/LIMIT 能下推到基表，走索引，性能好
TEMPTABLE 先把视图结果物化到临时表，再在外层过滤 全量计算后再裁剪，大表灾难

含聚合、DISTINCT、UNION、子查询的视图只能用 TEMPTABLE——上面的 v_user_consumption 就是。所以在 TEMPTABLE 视图上叠 WHERE 要警惕：WHERE user_id = 1 也是先算完全表再过滤。验证方法：EXPLAIN SELECT ... FROM 视图，看派生表（DERIVED）是否被全量物化。

可更新视图与 WITH CHECK OPTION

单表、无聚合、无 DISTINCT、无子查询的视图可以直接 INSERT/UPDATE/DELETE：

WITH CHECK OPTION 保证写入视图的数据必须满足视图定义条件，防止”写进去就看不见”的灵异数据。

避坑指南

  1. 视图不存数据、没有索引，它只省”写 SQL”的事，不省”执行”的事
  2. 基表删列后视图静默失效，查询才报错；定期 CHECK TABLE v_user_consumption 体检
  3. MySQL 没有物化视图，需要”预计算报表”就用汇总表 + 定时任务/触发器手动维护
  4. 视图的实用价值在权限收口：给 BI 账号只授权视图，基表结构随便改

二、字符串函数

基础操作

FIELD / ELT / FIND_IN_SET：集合三兄弟

FIND_IN_SET 的典型用法与深坑：很多老系统把多值塞进一个逗号分隔字段（如 tags = 'mysql,dba,tuning'），查询靠 WHERE FIND_IN_SET('dba', tags)。要清楚两件事：

  1. 完全无法走索引，数据量大必慢——这是反范式设计的代价，新系统老老实实用关联表
  2. 迁移旧系统时它是救命稻草，但目标应该是逐步拆表，而不是把 FIND_IN_SET 写进新代码

三、数值与类型转换函数

数值处理

坑：FORMAT 返回字符串，拿去做后续计算会触发类型转换；ROUND 是四舍五入，TRUNCATE 是直接砍——财务计算用错就是分钱对不上。

CAST / CONVERT 显式转换

隐式类型转换：比显式重要十倍的坑

MySQL 比较双方类型不同时会悄悄转换，规则是字符串转数字（从字符串开头解析数字，解析不了当 0）：

两个致命后果：

  1. 索引失效：phone 是 VARCHAR 却写 WHERE phone = 13800001111（数字），整列被隐式转换，索引直接报废（第四篇还会从执行计划角度再看一次）
  2. 误匹配：WHERE token = 0 能匹配所有非数字开头的 token——这是真实发生过的越权漏洞成因

四、日期时间函数

DATE_FORMAT 占位符速查（最常用）

占位符 含义 示例
%Y / %y 4位/2位年 2026 / 26
%m / %c 2位/无前导零月 08 / 8
%d / %e 2位/无前导零日 06 / 6
%H / %h 24时/12时 16 / 04
%i 分钟（不是 %m！） 05
%s 秒 09
%W / %w 星期名 / 星期数字(0=周日) Thursday / 4

避坑指南：日期查询头号性能坑

BETWEEN '2026-08-01' AND '2026-08-31' 查月份会漏掉 31 号当天 23:59:59 之后的数据（DATETIME 有秒/微秒精度），统一用 >= 月初 AND < 下月初。

避坑指南：JSON 使用边界

  1. 适合读多写少、结构多变的扩展属性；需要高频过滤/关联的字段必须提成正式列
  2. JSON 局部更新（JSON_SET）在 8.0 是部分更新（binary log 可只记 diff，需 binlog_row_value_options=PARTIAL_JSON），但整体仍不如列更新高效
  3. 别让 JSON 文档无限长大（单字段建议 < 64KB），它改变不了宽表变胖的事实

避坑指南：聚合查询的 NULL 三兄弟

  1. COUNT(列名) 不统计 NULL，COUNT(*) 统计所有行
  2. = NULL 永远 UNKNOWN；NOT IN (含 NULL 的子查询) 返回空集——经典线上 bug，用 NOT EXISTS 改写
  3. 8.0 默认 ONLY_FULL_GROUP_BY：SELECT 的非聚合列必须在 GROUP BY 里，别关它

函数 用途 备注

总结

  • 视图：MERGE 能下推、TEMPTABLE 先物化；权限收口是它的主战场
  • 函数用在 SELECT 随便用，用在 WHERE 的索引列上三思（DATE() 是最常见翻车点）
  • 隐式转换牢记”字符串转数字、失败归零”，0 = 'abc' 为真、索引失效两大后果
  • JSON：读用 ->>，写分清 SET/INSERT/REPLACE，过滤字段走虚拟列索引
  • 窗口函数：ROW_NUMBER 取 TopN、LAG 算环比、frame 控范围，LAST_VALUE 记得补完整 frame

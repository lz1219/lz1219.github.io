Spring Boot 配置文件加载顺序与优先级：本地、外部目录与配置中心全解析

Spring Boot 配置文件加载顺序与优先级：本地、外部目录与配置中心全解析

一个 key 到底读的是哪份配置，是 Spring Boot 项目里最容易产生”玄学问题”的地方：明明改了 application.yml 却不生效，最后发现是外部环境变量在覆盖；测试环境连上了生产库，因为 jar 同级目录躺着一个旧配置文件。这篇文章把默认搜索路径、外部目录指定、覆盖还是合并、配置中心与本地的优先级一次性讲透，并标出版本差异——因为 2.4 前后是两套装载机制，行为并不相同。

〇、先说结论（TL;DR）

Spring Boot 2.4+（含 3.x），不引入配置中心时，常见配置来源从高到低：

三条核心规律：

  1. 越靠近”运行时”的来源优先级越高：命令行 > 环境变量 > 外部文件 > jar 内文件
  2. 外部配置与 jar 内配置是”合并”关系：不是整文件替换，而是按 key 逐级覆盖
  3. 引入 Spring Cloud 配置中心后，远程配置默认插在”环境变量之下、本地文件之上”（legacy bootstrap 模式）；但 Boot 2.4+ 的 spring.config.import 新模式下，远程配置反而低于声明它的本地文件——这是升级后最常见的翻车点

一、版本差异：先确认你在哪套机制上

配置加载在 Spring Boot 2.4 被彻底重写，两套机制的行为差异直接影响结论：

维度 Boot ≤ 2.3（legacy） Boot 2.4+ / 3.x（Config Data）
加载器 ConfigFileApplicationListener ConfigDataEnvironmentPostProcessor
默认搜索位置 4 个 5 个（新增 file:./config/*/）
目录位置写法 结尾加不加 / 都识别 目录必须以 / 结尾
指定单个文件 允许不带文件名指定目录 必须写完整文件名，靠扩展名识别格式
位置可选性 默认可选 默认可选，可用 optional: 显式标注
导入外部配置 无 新增 spring.config.import（配置中心、configtree 都走它）
多文档 yml 覆盖 profile 文档无条件覆盖前面的文档 按文档物理顺序，后写的覆盖先写的
profile 文件内激活 profile 允许（但不推荐） spring.profiles.active 写在 profile 文件里直接启动报错
Spring Cloud 配合 bootstrap.yml 模式 spring.config.import 模式（bootstrap 需显式开启）

一句话：Spring Boot 2.4 及以上项目，忘掉 bootstrap.yml，用 spring.config.import；维护老项目时注意新规则，尤其是”目录必须带斜杠”和”多文档 yml 顺序变化”这两个静默行为变更。

1.1 追问：3.x 与 4.x 的具体差异

Boot 3.x（2022 年 11 月起）和 4.x（2025 年 11 月起）在配置加载机制上完全沿用 2.4 重写的 Config Data 模型——搜索路径、优先级顺序、spring.config.location/additional-location/import 的行为、覆盖规则都不变。差异在机制之外的几处：

维度 Boot 3.x Boot 4.x
基线 Java 17，Jakarta EE 9（javax.* → jakarta.*） Java 17+，Spring Framework 7，Jakarta EE 11，Jackson 3
legacy 开关 3.0 起删除 spring.config.use-legacy-processing（2.4–2.7 的过渡开关），老机制彻底不可用 同 3.x，无此开关
加载行为 与 2.4+ 一致 与 2.4+ 一致
属性键 少量重命名/移除 大量属性键重命名/移除（模块拆分所致），临时引入 spring-boot-properties-migrator 依赖可在启动时提示哪些键失效
构件结构 spring-boot 大 jar 模块化拆分（spring-boot-web、spring-boot-jdbc 等细粒度模块），自动配置按模块归位
对自定义扩展的影响 无 若你自写了 EnvironmentPostProcessor、ConfigDataLoader 等 SPI 扩展，需确认扩展类所在模块已引入依赖
对应 Spring Cloud 2021.x（Boot 3.0/3.1）、2022.x（3.2+）、2023.x 2025.x，配置中心仍走 spring.config.import，优先级规则不变

结论：如果你关心的是”配置到底谁覆盖谁”，3.x 和 4.x 的答案与本文完全一致；4.x 升级的真正工作量在属性键迁移（装 properties-migrator 跑一遍）和 依赖模块化调整，而不是加载规则。

二、默认搜索路径与加载顺序

2.1 五个默认位置

不设置任何 spring.config.* 时，Spring Boot 2.4+ 按以下顺序搜索 application.properties / application.yml（等价于内置了这条配置）：

后搜索的位置优先级更高，即优先级从低到高：

优先级 位置 说明
低 classpath:/ jar 内 resources 根目录
↓ classpath:/config/ jar 内 resources/config 目录
↓ file:./ 工作目录（通常即 jar 同级目录）
↓ file:./config/ 工作目录下的 config 子目录
高 file:./config/*/ config 下的一级子目录（按字母序，字母靠后的更高）

Boot ≤ 2.3 只有前四个位置，没有 file:./config/*/。

2.2 回答：jar 同级目录 vs classpath，谁赢？

jar 同级目录（file:./）赢。如果 myapp.jar 旁边放了一份 application.yml，它与 jar 内 classpath:/application.yml 合并，同一个 key 以外部那份为准。file:./config/ 里的优先级更高。

这正是官方推荐的”外部化配置”姿势：镜像/jar 一份通用，环境差异用外部文件覆盖。

2.3 同位置下 properties vs yml

同一目录同时存在 application.properties 和 application.yml 时，application.properties 优先级更高。项目里最好只保留一种格式，混用属于给自己埋雷。

2.4 profile 专属文件：跨位置也压普通文件

激活了 prod profile 后，application-prod.yml 与 application.yml 都加载，且：

  • 同一位置：application-prod.yml > application.yml
  • 跨位置也成立：jar 内的 application-prod.yml 优先级高于 jar 外的普通 application.yml

2.5 全景：完整的 PropertySource 优先级

文件只是链条中段，官方完整的属性源顺序（高 → 低）：

级别 来源 例子
1 命令行参数 java -jar app.jar --server.port=9090
2 SPRING_APPLICATION_JSON 内嵌 JSON SPRING_APPLICATION_JSON='{"server":{"port":9090}}'
3 Servlet 相关、JNDI web 应用场景
4 Java System 属性 -Dserver.port=9090
5 OS 环境变量 SERVER_PORT=9090
6 RandomValuePropertySource 只提供 random.*
7 jar 外部 profile 文件 file:./config/application-prod.yml
8 jar 内部 profile 文件 classpath:/application-prod.yml
9 jar 外部普通文件 file:./config/application.yml
10 jar 内部普通文件 classpath:/application.yml
11 @PropertySource 注解 自定义属性文件
12 SpringApplication.setDefaultProperties 代码里设的兜底默认值

环境变量的映射靠松散绑定（relaxed binding）：SERVER_PORT ↔ server.port，SPRING_DATASOURCE_URL ↔ spring.datasource.url（下划线转点，全大写转小写）。所以 K8s 里用 env 注入的配置，天然压过一切配置文件。

3.2 方式二：spring.config.location（替换默认，慎用）

注意它是整体替换默认搜索路径——只写 file:/opt/config/ 的话，jar 内的 application.yml 就完全不加载了。多数人想要的是方式一。

3.3 写法的硬性规则（2.4+）

  1. 目录位置必须以 / 结尾：file:/opt/config/ 是目录，会找里面的 application.yml/properties；file:/opt/config 会被当成文件名（然后因没有扩展名报错或忽略）
  2. 指定单个文件必须写全名：file:/opt/config/myapp-prod.yml，靠扩展名决定解析器
  3. 必须作为”环境属性”传入：命令行参数、-D 系统属性、OS 环境变量。写在 application.yml 里是无效的——加载文件之前位置就已经定了
  4. optional: 前缀表示位置不存在也不报错；不带 optional 且位置不存在时，默认只是跳过（spring.config.on-not-found=fail 可改为启动失败，2.4+ 行为有收紧，显式写 optional: 最稳妥）

这里必须先区分两种模式——它们的默认行为正好相反。

4.3 回答：加载顺序会不会影响结果？

会，而且就是优先级的实现机制本身。 所有属性源排成一条有序链，取 key 时从链头往下找，先命中先返回。所谓”优先级高”就是”在链上排得靠前”。所以：

  • 同一个 key 出现在多个来源 → 链上靠前的赢
  • 远程配置被拉取并插入链的时机与位置（bootstrap 插入 vs import 紧贴声明文档）直接决定它压谁、被谁压
  • 升级 Boot 2.4+ 后远程配置”失效”，十有八九是 import 模式的优先级反转，解法是把可覆盖项从声明 import 的那个文件里挪走，或把 import 声明移到更高优先级的外部文件

4.4 远程配置是启动时一次性加载的

配置中心改了值，运行中的应用不会自动生效。需要：

  1. 引入 spring-boot-starter-actuator 并暴露 refresh 端点：management.endpoints.web.exposure.include=refresh
  2. 对需要热更新的 Bean 加 @RefreshScope
  3. 调用 POST /actuator/refresh（单实例），或接 Spring Cloud Bus + 消息队列做广播刷新

@ConfigurationProperties 在 refresh 时会重新绑定；用 @Value 注入的字段则必须在 @RefreshScope 的 Bean 里才会更新。

五、避坑指南

坑 1：file:./ 相对的是工作目录，不是 jar 所在目录

file:./config/ 里的 . 是启动进程的工作目录。cd /opt/app && java -jar myapp.jar 时两者重合，但用 systemd 拉起时工作目录默认是 /，jar 旁边的配置文件根本不会被读到。解法：

Docker 里对应 WORKDIR。排查”配置没生效”时，先确认进程的工作目录（ls -l /proc/<pid>/cwd）。

坑 2：环境变量在看不见的地方覆盖

SERVER_PORT=9090 java -jar myapp.jar，改遍所有配置文件端口都是 9090——环境变量优先级高于一切文件。K8s 里 ConfigMap 以 env 注入时尤其常见。排查手段见第六节。

坑 3：以为 list 会合并

如 3.4 所述，集合类型是整体替换。想做”默认列表 + 追加项”，需要在代码层做合并逻辑，配置文件做不到。

坑 4：profile 文件里再激活 profile（2.4+ 直接报错）

application-prod.yml 里写 spring.profiles.active: inner，2.4+ 启动即抛 InvalidConfigDataPropertyException。profile 的激活只能在命令行、环境变量或非 profile 文档里做。

坑 5：多文档 yml 的顺序变化

同一个 yml 文件里用 --- 分多个文档，2.3 以前 profile 文档无条件压过前面的非 profile 文档；2.4 起按物理顺序，后写的文档覆盖先写的。老配置升级后行为可能反转，检查多文档文件时把通配配置放前面、profile 配置放后面。

坑 6：把密码写进命令行参数

--spring.datasource.password=xxx 会出现在 ps 输出和 shell 历史里。敏感值请走环境变量、配置中心（配合 {cipher} 加密值）或密钥管理服务。

六、验证手段：别猜，直接查

6.1 启动日志开 debug

2.4+ 会打印 Config data location 'file:./config/' does not exist 之类的装载细节，搜索了哪些位置一目了然。

6.2 /actuator/env 端点（最实用）

返回里会列出每个属性源中该 key 的值，第一个就是生效值，其余是被覆盖的。排查优先级问题的终极武器。注意 password、secret 等敏感 key 默认会打码显示（Boot 2.6+ 行为）。

七、生产建议

  1. jar 内 application.yml 只放通用默认值（应用名、 actuator 配置等），不放环境相关的连接串
  2. 环境差异放外部：单机部署用 file:./config/ 或 additional-location；多实例统一用配置中心
  3. 敏感配置走环境变量或配置中心加密，绝不进 jar、不进命令行参数
  4. 格式统一只用 yml 或只用 properties，避免同位置双格式
  5. 优先级的约定写进团队文档：比如”允许环境变量临时覆盖，禁止在服务器上散落 file:./ 配置”

总结

  • 默认搜索 5 个位置（2.4+）：classpath:/ < classpath:/config/ < file:./ < file:./config/ < file:./config/*/，jar 同级目录赢 classpath
  • 同位置 properties > yml；profile 文件压普通文件，跨位置也成立
  • 指定外部目录用 spring.config.additional-location（追加）；spring.config.location 是替换默认值，慎用；目录必须 / 结尾、文件必须带名、只能以环境属性方式传入
  • 外部与内部是合并 + key 级覆盖，但 list 是整体替换
  • 配置中心：legacy bootstrap 模式远程默认压本地文件（三个 override 开关可调）；spring.config.import 模式远程低于声明它的文档，升级后行为反转是高频坑
  • 优先级本质 = 属性源链上的顺序；远程配置启动时一次性拉取，热更新靠 /actuator/refresh + @RefreshScope
  • 排查优先级问题用 --debug 启动日志和 /actuator/env/{key}，别靠猜

Docker 镜像版本与更新策略：tag、digest 与 Compose 拉取实战

两个实际中高频遇到的问题：远程仓库更新了 myapp:latest，本地 docker compose up -d 却还在跑旧镜像；两个 tag myapp:v1.0 和 myapp:v1.1，怎么判断哪个内容更新、两个镜像内容是否完全一致。这两个问题背后是同一套知识：镜像的版本身份到底由什么决定。本文从实战命令讲到底层原理。

一、为什么 up -d 不拉新镜像

先看清 Docker Compose 的行为逻辑：up -d 只检查本地是否存在 compose.yml 里指定的镜像——存在就直接用，不存在才拉取。它不会主动比对本地镜像和远端镜像是否一致。

而 latest 这类可变 tag 只是仓库里的一个”指针”，远端推了新镜像后指针移动了，本地旧镜像却纹丝不动。于是出现了”本地 latest ≠ 远端 latest”的经典错位。

二、三种正确的拉取姿势

方案一：pull + up（显式两步，最稳）

为什么这能保证更新？ 拆开看两步各自的作用：

  1. docker compose pull：向仓库查询 tag 当前指向的 digest，与本地不一致就拉取，本地 tag 指针随之更新
  2. docker compose up -d：检测到容器当前使用的镜像 ID 与 compose 解析到的镜像 ID 不一致，自动重建容器

所以只要 pull 成功拿到了新镜像，up 就一定会重建——这个组合是可以保证更新的。反过来，如果 pull 发现远端没变化，up 检测到无变化就什么都不动，也不会无故重启服务，行为刚刚好。

方案二：up 时直接带 –pull（较新版本 Compose）

--pull 在 up 阶段控制拉取策略，三个取值：

取值 行为
always 每次 up 都先尝试拉取最新镜像（等价于自动执行了方案一的第一步）
missing（默认） 仅本地没有时才拉取——这就是”不更新”的默认行为
never 从不拉取，只用本地镜像

使用前确认你的 Compose 版本支持：docker compose version，以及 docker compose up --help 里能看到 --pull 参数（Docker Compose v2 的较新版本支持，老版本请用方案一或升级）。

方案三：写进 compose.yml（配置固化）

不想每次记参数，就在服务定义里声明 pull_policy：

三种方案的选择：临时操作用 --pull always，长期行为固化到 pull_policy，脚本/CI 里用 pull && up 组合（退出码语义最清晰，pull 失败可以及时中止不启动）。

避坑指南：三个容易混淆的点

  1. --force-recreate 只重建容器，不拉镜像——它解决的是”配置没变也想重启”，和镜像更新完全是两回事
  2. docker compose restart 同理，只是重启现有容器，镜像、配置变化都不感知
  3. 本地 build 的镜像（compose 里有 build: 段）不受 pull 策略影响——那种情况用 docker compose up -d --build 强制重建镜像

三、常用命令到底干了什么（原理解剖）

理解命令背后的机制，才能预判它的行为。先补一个底层概念，再逐个解剖。

铺垫：镜像是分层的，容器是”镜像 + 可写层”

Docker 镜像由一组只读层（layer）叠成，每层是上一层之上的文件变更集。启动容器时，Docker 用 overlay2 联合文件系统把所有只读层挂载合并，再在最上面盖一层可写层（container layer）：

  • 容器里看到的完整文件系统 = 只读镜像层（共享）+ 顶部可写层（私有）
  • 容器内改文件 = 写时复制（copy-on-write）：把镜像层的文件复制到可写层再改，原镜像层不动
  • 这就是”删容器数据就没了”的原因——可写层随容器删除，镜像层还在（也是数据卷存在的意义）

多个容器跑同一镜像时，只读层完全共享，100 个容器也只占一份镜像空间。

docker pull：不是”下载一个镜像”，是按层取差量

  1. 向仓库请求 latest 指向的 manifest，拿到 digest 和所有层的摘要列表
  2. 逐层检查本地是否已有该层（按层 digest 判断）——已有的层直接跳过，这就是”Already exists”那几行
  3. 只下载缺失的层，解压组装
  4. 本地 tag 指针更新到新 manifest

所以 pull 是差量更新：新版本只改了两层，就只下载两层。这也是为什么镜像个头几 GB、更新往往只有几十 MB。

docker run：一条命令 = create + start

docker run 实际做了两件事：docker create（基于镜像造出容器：分配可写层、网络、环境变量）+ docker start（启动入口进程）。

关键认知：容器的本质是宿主机上的一个进程（靠 namespace 隔离视图、cgroups 限制资源），入口进程（PID 1）退出 = 容器退出。--restart unless-stopped 这类策略就是 Docker 守护进程在容器退出后自动重新拉起。

docker build：逐指令生成层，缓存按指令链判断

每条 Dockerfile 指令产生一层。构建缓存的判断逻辑：从第一条指令开始，只要某条指令的内容（包括 COPY 的文件内容哈希）和上次一致，就复用该层及其所有父层；一旦某层缓存失效，后面所有层全部重建。

这就是为什么”依赖安装放前面、代码 COPY 放最后”——代码天天变，让它排在最后，前面的依赖层才能稳定命中缓存。

docker exec：在容器的 namespace 里开新进程

不是”登录进容器”（容器里没有 SSH），而是 Docker 通过 setns 把新进程（bash）塞进容器的 namespace，于是它看到和容器主进程相同的文件系统、网络、进程空间。主进程挂了，exec 的 shell 也随之消失。

docker stop 与 docker kill：信号的区别

应用收不到 SIGTERM 就无法优雅停机（断连、刷盘）。常见坑：用 sh -c 或 shell 脚本包一层启动应用时，信号被 shell 截获传不到应用——Dockerfile 里 ENTRYPOINT 用 exec 数组形式（["java", "-jar", ...]）才能让应用直接当 PID 1 收信号。

docker logs：读的是容器主进程的 stdout/stderr

Docker 默认用 json-file 日志驱动，把容器 PID 1 的标准输出/错误落盘成 JSON 文件，docker logs 就是读这个文件。两个推论：

  • 应用日志写文件而不是打 stdout 的，docker logs 什么都看不到——这是容器日志设计的第一原则
  • 长期不清理会撑爆磁盘：生产配置 log-opts max-size=10m max-file=3

docker compose up：一次完整的编排流程

docker compose up -d 背后做了一连串事：

  1. 解析 compose.yml，构建项目模型（服务、网络、卷、依赖顺序）
  2. 创建项目级网络（不存在才建）和命名卷
  3. 对每个服务解析镜像（受 pull_policy/–pull 控制是否先拉取）
  4. 逐个服务比对现有容器与期望状态：镜像 ID、环境变量、端口、卷、重启策略等有任何差异 → 停掉旧容器重建；无差异 → 保持不动（这就是”幂等”）
  5. 按 depends_on 顺序启动容器，后台化（-d）后打印各容器状态

理解了第 4 步，就理解了为什么改 compose.yml 后 up 会自动重建、什么都没改时 up 秒回”什么都不做”。

docker compose down：清场清单

不会动的：镜像（默认）、bind mount 的宿主目录、外部创建的 volume。删容器丢数据、删卷毁数据的区别就在这里。

docker compose ps / logs：面向项目的视图

docker compose ps 只列当前项目（compose 项目名隔离）的容器，是 docker ps 的过滤版；docker compose logs -f app 把指定服务容器的 stdout 聚合跟踪，等价于自动找到对应容器再 docker logs -f。

四、镜像身份三要素：Image ID、tag、digest

要比较镜像版本，先搞清楚三个常被混为一谈的概念：

概念 本质 特点 查看方式
Image ID 镜像配置（config JSON）的 SHA256 本地唯一标识，跨机器无意义 docker images 的 IMAGE ID 列
tag 人类可读的名字（如 myapp:v1.0） 可变指针：可以移动、复用、删除，多个 tag 可指向同一镜像 docker images 的 TAG 列
digest 镜像清单（manifest）的 SHA256，形如 sha256:abc... 内容寻址：内容变 digest 必变，仓库中的全局唯一身份 docker images --digests、docker inspect 的 RepoDigests

三者的关系：tag 是指向 digest 的可变标签，Image ID 是镜像在本地的身份证。同一个镜像可以有多个 tag；latest 没有任何特殊性，只是 Docker 在你不写 tag 时默认填上的一个普通标签。

五、如何比较两个镜像的版本与内容

标签字符串：不能作为比较依据

v1.0 和 v1.1 看起来有大小，但 tag 只是任意字符串：

  • 字典序不等于时间序：v1.9 字典序大于 v1.10
  • 语义化版本靠团队自觉维护，Docker 本身不理解版本号
  • tag 可以被重新指向旧代码（回滚发版时 v1.1 可能指回旧构建）

创建时间：可参考但不可靠

docker images 的 CREATED 列是镜像构建时间，比 tag 有参考价值，但仍有陷阱：旧代码完全可以重新构建（hotfix 回灌、rebuild），时间新不代表代码新。

digest：内容判等的唯一标准

判断两个镜像内容是否完全一致，用 digest：

digest 相同，则两个 tag 指向的 manifest 完全相同，内容必然一致（manifest 覆盖 config + 所有层的信息）。这是唯一能下”完全一致”结论的依据。

但反向有个重要细节：digest 不同 ≠ 代码不同。镜像 config 里包含构建时间戳等元数据，同一份代码构建两次，digest 也会不同。想判断”代码是否相同而元数据不同”，要逐层比对 layer digest（imagetools inspect 输出里有各层摘要）——层全一致而顶层 config 不同，说明只是构建时间不同。做可复现构建（reproducible builds，固定 SOURCE_DATE_EPOCH）的团队可以跳过这个烦恼。

多架构的坑：manifest list digest vs 平台 digest

现代镜像多是多架构（amd64/arm64）的 manifest list。注意有两层 digest：

  • manifest list digest：整个多架构镜像的 digest，docker images --digests 和仓库显示的都是它
  • 平台 manifest digest：某个具体架构镜像的 digest

比较时要用同一层级的 digest，拿本地的 manifest list digest 去比远端某个平台的 digest，永远对不上。

六、实战工作流

判断本地 latest 是否落后于远端

勘误：RepoDigests 是个数组，{{index .RepoDigests 0}} 不可靠

很多教程（包括本文早先版本）写 {{index .RepoDigests 0}} 取第一个 digest，这在镜像只有单个 tag、且只从单个仓库拉过时没问题。但一旦同一镜像有多个 tag、或从多个 registry mirror 拉取过，RepoDigests 里会有多条 仓库@sha256:... 记录，数组顺序不保证，取第一个可能拿到的是别的仓库的 digest，比对永远对不上。正确做法是像上面一样全量列出，再按仓库名过滤（grep 'registry.example.com/myapp@'），或直接看 docker images --digests 中对应 tag 那一行。

更新的代价：单副本更新必然有停机

一个容易被忽略的事实：docker compose up -d 检测到镜像变化后的动作是先停旧容器、再启新容器，单副本服务在两者之间存在几秒到几十秒的服务中断（取决于应用启动速度）。缓解手段分几层：

  1. 缩短启动时间：让应用快速就绪，比什么编排都实在

  2. 配健康检查 + 依赖条件：多服务场景下，让依赖方等被依赖方”健康”而不是仅”启动”：

  3. 接受维护窗口：内部系统、低频服务，挑低峰期更新即可，这不是缺陷

  4. 真正的零停机：需要多副本 + 负载均衡滚动替换，或蓝绿部署——这已经超出单机 Compose 的能力边界，该上 Swarm/K8s 或者至少前置一个反向代理做双实例切换了

健康检查的另一个价值：没有 healthcheck 时 Compose 认为容器”启动即成功”，应用还在初始化（比如 Java 服务预热 30 秒）流量就打进来了。配了 healthcheck 后，docker compose ps 会显示 healthy/unhealthy 状态，排障时一眼可见。

团队约定：固定 tag 与浮动 tag 怎么配合

只发 v1.2.3 固定 tag 的镜像，消费者想跟进补丁更新就得逐个改版本号；只发 latest，又完全不可控。务实的做法是三级 tag 同时推送：

三个 tag 指向同一 digest，语义不同：

tag 语义 适合谁用
v1.2.3 钉死这一个版本，永不复用 生产环境
v1.2 跟随 v1.2.x 最新补丁（发 v1.2.4 时此指针移动） 愿意自动收补丁修复的测试环境
v1 跟随 v1.x 最新（含新特性，不含破坏性变更） 对兼容性有信任的周边工具

这要求发布方遵守语义化版本纪律：破坏性变更必须升主版本号。消费者按自己的风险承受度选择引用层级——这就是”浮动 tag”的正确用法：不是不用，而是明知它在浮动、且浮动范围符合预期。

别忘了清理：悬空镜像与磁盘占用

每次重新构建、每次 latest 漂移，旧镜像不会自动消失。本地会积累两类垃圾：

  • 悬空镜像（dangling）：docker images 里 <none>:<none> 的那些。构建新镜像把 tag 抢走后，旧镜像失去名字就成了悬空镜像，纯占磁盘
  • 不再被引用的旧版本镜像：比如升完 v1.2.4 后留下的 v1.2.3

构建缓存往往比镜像更占空间，docker builder prune 单独清它。

registry 侧的对应问题：删 registry 里的旧 tag（或在 Harbor 等项目里删镜像）通常只是删了 manifest 引用，层数据不会立即释放，需要 registry 执行垃圾回收（GC）才真正回收空间。 Harbor 用户可以在项目里配保留策略（retention policy，如”每个仓库保留最近 10 个 tag”）+ 定时 GC，否则私有仓库磁盘会被无休止的历史版本撑爆。

生产环境别用 latest（最后强调）

latest 的一切问题都源于”可变指针 + 本地缓存”的组合。生产环境的纪律：

  1. 每次发布打语义化版本 tag（v1.2.0），且 tag 一旦发布永不复用
  2. compose.yml 里写死版本号或 digest，不写 latest
  3. latest 可以保留给开发环境快速迭代，但要有”它随时漂移”的自觉

七、拉取失败排查：认证与镜像加速

pull / --pull always 配好了，结果一执行就报错——这是仅次于”不更新”的高频问题。集中讲两类。

私有仓库认证：unauthorized 怎么破

拉私有镜像报错 unauthorized: authentication required 或 pull access denied，就是没登录或凭证失效：

几个实战要点：

  • 凭证存哪：~/.docker/config.json 的 auths 字段，key 是 registry 域名，value 是 base64 编码的 用户名:密码（不是加密！）。配了 credsStore 的系统（如 Docker Desktop 用系统钥匙串）则存到外部凭证助手里
  • 登录的是域名不是仓库：docker login 不带参数默认登 Docker Hub（docker.io），私有仓库必须带完整域名，否则凭证存错条目，拉取照样 401
  • CI 里别交互式登录：用 --password-stdin 避免密码进 shell 历史：echo "$TOKEN" | docker login registry.example.com -u ci-bot --password-stdin
  • Harbor/GitLab 等建议用机器人账户或 Access Token，不要拿个人密码进流水线
  • Compose 与登录的关系：docker compose pull 复用 Docker CLI 的同一套凭证，login 一次两边通用

  • daemon.json 改完必须重启 Docker 才生效，且 JSON 语法错误会导致 Docker 起不来，改之前备份

总结

  • 镜像是只读层的叠加，容器 = 镜像层 + 可写层；pull 按层差量下载，up 按期望状态幂等重建
  • docker compose pull && docker compose up -d 能保证更新：pull 移动本地 tag 指针，up 检测到镜像 ID 变化必然重建
  • up -d --pull always 一步搞定（新版 Compose）；长期行为写 pull_policy: always；--force-recreate 与拉取无关
  • tag 是可变指针，不能比大小；创建时间可参考不可靠；内容判等的唯一标准是 digest
  • digest 相同必同内容；digest 不同未必不同代码（构建时间戳差异），精细比对看 layer digest
  • 比对本地与远端时，RepoDigests 是数组，全量列出再按仓库过滤，别盲取第一个元素
  • 三级 tag（v1.2.3 / v1.2 / v1）让消费者按风险承受度选引用层级；浮动 tag 的关键是浮动范围符合预期
  • 单副本 up -d 更新 = 先停后启必然有停机；健康检查让依赖方等”就绪”而非”启动”，零停机要超出单机 Compose 的能力
  • 悬空镜像靠 docker image prune，registry 侧删 tag 不释放空间，需保留策略 + GC 配套
  • 私有仓库拉取失败先查认证（login 的是域名），Docker Hub 拉不动配 registry-mirrors（只加速 docker.io）或守护进程代理
  • 生产部署：语义化版本 + digest 引用，环境一致性和回滚精确性都靠它

相关的容器基础可以参考之前的《Docker 常用命令与核心知识总结》。
